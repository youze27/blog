终端防御规避技术-6.文件系统微筛选器

卷卷原创2026/10/28大约 21 分钟应急响应应急响应EDR终端防御与规避免杀文件系统微筛选器Minifilter命名管道

进程、线程、句柄、模块，前几章的传感器看的都是内存里的事。文件从网络落到磁盘、从磁盘再进内存的这段路，它们只能在程序关闭句柄、映像加载完成这些节点上看到结果。中间谁写了哪个文件、写了多少、改了什么名字，全归文件系统微筛选器管。

EDR 的落地扫描、勒索行为识别、安装目录自保护都挂在这一层，命名管道这类横向移动和 C2 常用的通道也归它看。攻击者要让文件检查失灵，或者让管道通信不被记录，主要也从这一层动手。

1. 微筛选器到底是什么

Windows 上的读写最终落到某个卷上的文件系统，比如 NTFS。想在这条路上插一脚的安全产品，都得在文件系统上面挂一个过滤驱动。

老办法是驱动自己调用 IoAttachDeviceToDeviceStack，挂到卷的设备栈上，然后亲自处理 IRP：包怎么拆、完成例程怎么挂、文件名怎么查、上下文怎么存，全得自己写。这套写法繁琐，几个产品装在一起时谁先谁后还由加载时间决定。先装杀软再装加密软件，和反过来装，文件栈的顺序不一样，拿到的是明文还是密文也不一样，冲突和蓝屏大多出在这里。

Vista 之后微软引入了过滤管理器 fltmgr.sys，把这些杂活收拢起来。驱动不再直接去挂设备栈，而是向 FltMgr 注册一个微筛选器（minifilter），声明自己的 altitude。FltMgr 负责按 altitude 把微筛选器插进每个卷的栈里，负责把 IRP 包装成统一的 PFLT_CALLBACK_DATA，负责文件名解析、上下文分配和引用计数。驱动只需要实现几个回调函数。

把卷的文件栈想成一条分拣线：应用把包裹放上流水线，FltMgr 是分拣中心，按工位编号决定包裹先过哪个工位。微筛选器就是线上的检查工位，编号大的在前，先看到包裹。想查文件内容的产品，工位基本都在杀软号段。

微筛选器只有内核驱动这一种形态，必须签名，必须按 WDK 的模型写。任何声称能做文件监控的 EDR，内核里都躺着这么一个驱动。

1.1 实例与上下文

微筛选器注册一次，但对每个卷要单独挂一个实例（instance）。InstanceSetup 在挂载时被调用，返回 STATUS_FLT_DO_NOT_ATTACH 就跳过这个卷。网络盘、可移动介质、产品策略里不保护的卷，都可能在这一步被排除。

实例之上还有上下文（context）。实例上下文、卷上下文、文件上下文、流上下文、流句柄上下文，驱动可以在文件对象上挂一小块自己的数据，同一个文件后续的回调里直接取出来，不必每次重查。分配和引用计数由 FltMgr 管，驱动漏了释放，FltMgr 会兜底。

上下文为什么重要

一次文件操作可能穿过好几个回调：创建、写入、清理。如果每次都在回调里重新查路径、重新算哈希，开销会非常大。文件上下文让驱动在第一次创建时把判断结果挂上去，后面的写入和清理直接读。这个设计也带来一个副作用：上下文是按文件对象或流存的，换个句柄打开同一个文件，拿到的可能是另一份上下文。

1.2 它和老式过滤驱动的差别

对比项老式过滤驱动微筛选器
挂载方式自己调 IoAttachDeviceToDeviceStack注册后由 FltMgr 挂载
处理对象原始 IRPPFLT_CALLBACK_DATA
顺序控制加载时间altitude 号段
文件名解析自己做FltGetFileNameInformation
上下文自己实现FltMgr 管理
能看到的东西IRP 全部字段FltMgr 暴露的接口

少掉的那部分自由也是代价：微筛选器看不到 IRP 的原始结构，某些冷门字段和特殊路径拿不到，得绕道别的接口。

2. 一次 WriteFile 走过哪些层

应用调用 WriteFile，I/O 管理器把请求打包成 IRP，逐层往下传。

应用 WriteFile
  | I/O 管理器生成 IRP（IRP_MJ_WRITE）
  v
过滤管理器 FltMgr
  | 按 altitude 从高到低分发
  +--> minifilter A  420000  Top
  +--> minifilter B  320000  Anti-Virus
  +--> minifilter C  140000  Encryption
  v
NTFS
  v
卷管理器 / 磁盘

altitude 决定顺序。数值大的靠近应用，先看到请求；数值小的靠近文件系统，后看到。杀软号段在 320000 附近，加密驱动在 140000 附近。同一份数据，杀软先看到明文，加密驱动后加密，这个顺序对检测很关键。反过来的话，杀软拿到的就是密文，静态规则全部失效。

号段用途
420000–429999Top
400000–409999Activity Monitor
320000–329999Anti-Virus
180000–189999HSM
140000–149999Encryption
20000–29999Bottom

号段由微软分配，具体值以官方文档为准。

IRP 是什么

应用调 WriteFile，I/O 管理器把这次请求打包成一个 I/O Request Packet，里面带目标文件对象、数据缓冲区、长度、偏移、发起进程。驱动程序逐层处理这个包，每一层都可以检查、修改、放行或拒绝。minifilter 回调拿到的 PFLT_CALLBACK_DATA 就是包装过的 IRP，Data->Iopb 里是这次操作的参数。

3. 注册与回调

const FLT_OPERATION_REGISTRATION Callbacks[] = {
    { IRP_MJ_CREATE,          0, PreCreate,  PostCreate  },
    { IRP_MJ_WRITE,           0, PreWrite,   PostWrite   },
    { IRP_MJ_SET_INFORMATION, 0, PreSetInfo, PostSetInfo },
    { IRP_MJ_CLEANUP,         0, PreCleanup, NULL        },
    { IRP_MJ_OPERATION_END }
};

const FLT_REGISTRATION Registration = {
    sizeof(FLT_REGISTRATION), FLT_REGISTRATION_VERSION,
    0, Contexts, Callbacks,
    FilterUnload, InstanceSetup, InstanceQueryTeardown,
    InstanceTeardownStart, InstanceTeardownComplete,
    NULL, NULL, NULL
};

FltRegisterFilter(DriverObject, &Registration, &g_FilterHandle);
FltStartFiltering(g_FilterHandle);

回调原型：

FLT_PREOP_CALLBACK_STATUS PreWrite(
    PFLT_CALLBACK_DATA Data,
    PCFLT_RELATED_OBJECTS FltObjects,
    PVOID *CompletionContext);

返回值决定后面怎么走：

返回值含义
FLT_PREOP_SUCCESS_NO_CALLBACK放行，不调 post
FLT_PREOP_SUCCESS_WITH_CALLBACK放行，完成后调 post
FLT_PREOP_COMPLETE直接完成，不再往下传
FLT_PREOP_DISALLOW_FASTIO禁用快速 I/O，强制走 IRP 路径
FLT_PREOP_SYNCHRONIZEpost 在发起线程同步调用

pre 能拦，post 只能看

pre 回调在请求下发到文件系统之前执行，返回 FLT_PREOP_COMPLETE 就把这次操作直接结束掉，相当于当场拒绝。post 回调在文件系统处理完之后执行，只能观察结果，改不了。杀毒软件的创建拦截全部落在 pre。

常用的事件类型

IRP_MJ_CREATE 覆盖打开和创建，IRP_MJ_WRITE 覆盖写入，IRP_MJ_SET_INFORMATION 覆盖重命名、删除、设置长度、分配空间，IRP_MJ_CLEANUP 在最后一个用户句柄关闭时触发，IRP_MJ_ACQUIRE_FOR_SECTION_SYNCHRONIZATION 在文件被映射成 section 时触发。

挂在哪个卷上

minifilter 按卷挂实例，InstanceSetup 里可以决定挂不挂。返回 STATUS_FLT_DO_NOT_ATTACH 就跳过这个卷，比如网络盘、可移动介质，或者产品策略里不保护的卷。

4. 回调里能拿到什么

文件对象、卷、实例都能从 FltObjects 取到；操作参数在 Data->Iopb 里：Write.Length、Write.WriteBuffer、Write.ByteOffset，创建操作的 DesiredAccess 也在里面。

发起进程用 FltGetRequestorProcessId 取 PID，再 PsLookupProcessByProcessId 查 EPROCESS。进程名还是那 15 个字符的短名，和进程创建通知里遇到的是同一个限制。

文件名要单独查

PFLT_FILE_NAME_INFORMATION nameInfo;
FltGetFileNameInformation(Data,
    FLT_FILE_NAME_NORMALIZED | FLT_FILE_NAME_QUERY_DEFAULT, &nameInfo);
FltParseFileNameInformation(nameInfo);

FltGetFileNameInformation 只能在 PASSIVE_LEVEL 调用，回调不满足这个条件时得把请求丢到工作线程。文件正在改名或者已经删除时，名字查询会失败，EDR 要准备降级方案：从 FileObject 反查，或者用卷和文件 ID 定位。

内容不一定在缓冲区里

WriteBuffer 只在非缓存写入时有效。缓存写入的数据在 Cache Manager 里，minifilter 拿不到那一段；分页写入（刷脏页）走的是另一条路径。想扫描完整内容，通常等文件关闭再读整份。

5. 扫描时机

时机能做什么代价与盲区
IRP_MJ_CREATE（带执行意图）在执行前拦截文件可能刚创建，内容还是空的
IRP_MJ_WRITE逐次检查写入内容开销大，缓存写入拿不到
IRP_MJ_CLEANUP关闭句柄时读整份扫描恶意程序可以在关闭前执行
IRP_MJ_ACQUIRE_FOR_SECTION_SYNCHRONIZATION监控映像映射只看到映射动作，看不到内容

为什么多在 CLEANUP 扫描

写入过程中文件不完整，逐块扫描又慢又容易误判。关闭句柄时内容定型，读一遍算哈希、跑规则、做静态分析都合适。代价是"写完不关句柄直接执行"能绕开这个时机，所以创建阶段的执行拦截不能省。

扫描不能卡住写入线程

一个 500 MB 的安装包在关闭时做全量扫描，同步执行的话用户会明显感觉卡顿。EDR 通常把扫描丢到工作线程，先放行访问，扫出问题再阻断后续执行或者删除文件。这中间有一个时间窗：扫描完成前，文件可能已经被执行过一次。真正要紧的文件，创建时带执行意图就直接拦。

6. 用微筛选器盯住攻击行为

文件系统层的传感器看三样东西：谁在动文件、动的是哪个文件、动的动作是什么。把这三样和时间、频率、上下文串起来，就能还原出大部分落地和持久化行为。

6.1 文件监测

同一次恶意行为，往往会同时触发好几个回调：

攻击行为落到哪个回调观察点
下载落地IRP_MJ_CREATE + IRP_MJ_WRITE进程是浏览器、PowerShell 还是 Office；路径在临时目录还是用户目录
释放载荷IRP_MJ_WRITE写入内容含 PE 头、高熵、大小异常
改名伪装IRP_MJ_SET_INFORMATION（重命名）从 .tmp 改成 .docx、.pdf、.lnk
删除痕迹IRP_MJ_SET_INFORMATION（删除）+ CLEANUP安装后删除释放的文件
修改时间戳IRP_MJ_SET_INFORMATION（基本信息）文件时间被改成系统文件的年份
写入备用数据流IRP_MJ_CREATE，名字带流名路径形如 a.txt:payload.exe
映射成映像IRP_MJ_ACQUIRE_FOR_SECTION_SYNCHRONIZATION新建的可执行文件紧接着被映射
句柄不关就执行IRP_MJ_CREATE 带执行意图前一个写句柄还没清理

单个回调的信息量很小。一个 powershell.exe 往临时目录写文件，可能是系统管理脚本，也可能是下载器；差别在前后文：这个文件随后有没有被映射、有没有被另一个进程以执行方式打开、写入者的父进程是谁、文件是不是刚从网络来的。

命名管道的监测也是同样的思路，只是对象换成了管道。

6.2 命名管道监测

命名管道是 npfs.sys 提供的文件系统对象，用户态路径是 \\.\pipe\<名字>，内核里对应 \Device\NamedPipe\<名字>。服务端调用 CreateNamedPipe（内核接口 NtCreateNamedPipeFile），客户端用 CreateFile 打开这个路径，双方像读写文件一样收发数据。

从 I/O 管理器的角度看，创建和打开管道仍然是 IRP_MJ_CREATE，读是 IRP_MJ_READ，写是 IRP_MJ_WRITE，断开是 IRP_MJ_CLEANUP。管道不是某个卷上的文件，而是 NPFS 这个文件系统里的对象，所以微筛选器看到的文件名是设备路径，不是 C:\ 开头的那种。Sysmon 的驱动就是一个微筛选器（altitude 385201），管道创建和连接事件就是从这里出来的。也有产品改用对象回调或者 ETW 补这一块，因为管道文件系统的挂载方式和普通卷不完全一样。

管道值得单独监控，因为横向移动和 C2 大量用它：

  • PsExec 把服务端程序推到远端，注册成服务运行，服务进程建一个 \\.\pipe\PSEXESVC 管道，客户端连上来之后，命令和输出都从管道走。
  • SMB beacon 这类 C2 通道把数据塞进命名管道，管道名由操作者配置，常见一串没意义的随机字符。
  • 低权限进程连上高权限服务的管道，服务端调用 ImpersonateNamedPipeClient 借用客户端的令牌，攻击者反过来做假管道等 SYSTEM 来连，就能拿到 SYSTEM 身份。
  • 本地侦察时会枚举 \\.\pipe\，找安全软件的管道、浏览器的 IPC 端点、RPC 接口。

监测的维度：

维度正常样子异常样子
创建者服务进程、系统组件用户目录里的进程、Office、脚本宿主
管道名有明确含义，如 lsarpc、PSEXESVC高熵随机串、仿冒系统管道名
客户端来源本地进程远端主机通过 SMB 连入
数据方向少量控制消息创建后立即大流量双向读写
是否模拟常规调用服务端对客户端调用 ImpersonateNamedPipeClient
生命周期长期存在建起、传完、立刻关闭

只按管道名做黑名单，误报会很难看：浏览器、杀软、数据库都有自己的管道，名字还会随版本变。真正有用的是把创建者、名字特征、连接来源三件事放在一起看。

管道这条路的规避

管道名随机化，按已知工具名匹配的规则就失效了。C2 从 SMB 管道换成 TCP 或 HTTPS，管道监测直接看不到。借已经存在的合法管道传数据，看起来就是正常组件在通信。本地短距离传递用匿名管道，匿名管道不在 \\.\pipe\ 命名空间里，枚举不到。还有一种是让合法客户端去连，比如通过 net use、远程服务控制，发起进程是系统自带程序。

7. 让传感器失效：卸载防护与对抗

7.1 为什么攻击者想先卸载

停掉一个驱动，等于同时关掉落地扫描、勒索识别、目录自保护和一部分行为关联。比逐条规则去绕省事得多。真实入侵里"先干掉安全软件再干活"很常见，所以 EDR 厂商在"不允许自己被卸载"这件事上投入的精力，不比检测规则少。

7.2 EDR 这边的几道锁

驱动拒绝停止

驱动对象里的 DriverUnload 置空。没有卸载例程的驱动，服务控制管理器不接受停止请求，sc stop 返回 1052（服务无法接受控制消息）。服务的安全描述符只留给 SYSTEM 和 TrustedInstaller，普通管理员连 sc delete、sc config 都执行不了。

进程与服务保护

EDR 的服务进程注册为受保护进程（PPL，anti-malware light 级别），安装时在服务键下写 LaunchProtected。再配合 ELAM 驱动：它以 boot-start 方式在系统启动早期加载，签名经过启动校验流程，比普通驱动先起来。普通管理员即使拿到 SYSTEM 令牌，也打不开 PPL 进程，改不了它的服务配置。

文件自保护

自己的 minifilter 在 pre-create 里拒绝带 DELETE 或写权限的打开请求，保护安装目录、驱动文件、配置文件、隔离区。攻击者能删掉别的文件，删不掉 EDR 自己的。这一层和第四章的对象回调配合：对象回调挡打开进程的句柄，minifilter 挡改文件的句柄。

互相守护与遥测

两个驱动互查对方是否还在跑，一个被停另一个负责恢复或者报警。内核和用户态服务之间通过通信端口（FltCreateCommunicationPort）交换配置和事件。用户态服务被杀，驱动可以选择两种策略：关键操作一律拒绝（fail-closed），或者继续放行但只记录（fail-open）。多数产品在自保护类操作上选前者。

启动链完整性

服务设为 boot-start，篡改注册表要等重启才生效。重启时 ELAM 先跑，驱动加载顺序和签名都会再校验一遍，临时改注册表的做法很容易在这里露馅。

7.3 攻击者怎么绕这几道锁

锁绕过手法代价与失败点
驱动拒绝停止用带漏洞的签名驱动（BYOVD）在内核里直接调 FltUnregisterFilter，或者把 FLT_FILTER 里的回调指针改空需要内核读写能力；易受攻击的驱动常在黑名单里；结构偏移算错直接蓝屏
PPL 进程内核层改 EPROCESS 的保护位，或者借合法驱动代为操作需要内核写；改保护位会触发系统完整性检查；操作痕迹明显
服务 ACL先拿到 SYSTEM 或 TrustedInstaller 令牌，再改服务配置改动进注册表，重启后才生效；服务配置变更会留事件
文件自保护走直接卷访问，绕开 minifilter 改驱动文件要自己解析 NTFS；卷句柄访问本身显眼；文件哈希对不上
互相守护同时停掉两个驱动或两个服务时间窗很短，漏一个就会触发告警
遥测防火墙拦出站、代理劫持、DNS 污染本地拦截还在，告警出不去；出站异常和心跳缺失本身就是信号

BYOVD 是这几年最常用的路子：找一款有任意内核读写漏洞的合法签名驱动，加载进来，用它读写内核内存。拿到读写之后能干的事很多，摘进程创建回调、摘镜像加载回调、摘对象回调、摘注册表回调，也可以动微筛选器。它的难点不在写代码，在于找驱动、算偏移、避开微软的易受攻击驱动黑名单（HVCI 开启时更麻烦）。

7.4 不卸载也能干扰

卸载动静大，容易被发现。更多攻击者选择让传感器"还在，但没用"：

  • 阻断回传。驱动照旧拦截，事件发不出去，云端关联和人工处置全都断掉。出站流量里 EDR 的心跳、云查请求消失，是很明显的信号。
  • 干扰扫描。塞超大文件、压缩炸弹、海量小文件，把扫描队列堵死，让后续样本超时跳过。表现为扫描队列积压、磁盘 IO 和 CPU 异常、大量超时日志。
  • 抢在扫描前执行。写完文件不关句柄，立刻以执行方式打开。CLEANUP 扫描还没轮到，代码已经跑起来。
  • 打时间差。在 EDR 更新规则、重启服务、升级驱动的窗口里动手。

7.5 防守方看哪里

服务状态变化（系统日志 7045 新服务、7040 服务配置变更、7036 服务状态）、驱动加载（Sysmon 事件 6）、进程终止（4689）、注册表服务键被改、卷设备被打开、管道异常创建，这几类事件放在一起，基本能拼出"有人在动安全软件"的轮廓。

8. 不碰驱动也能规避文件监测

8.1 直接卷访问

CreateFile("\\.\C:", GENERIC_READ | GENERIC_WRITE, ...)
  -> 解析 NTFS，定位目标文件的簇
  -> SetFilePointer(簇偏移)
  -> WriteFile(扇区对齐的数据)

这条路径不经过文件系统，FltMgr 和 minifilter 都看不到。需要管理员权限，还要自己解析 NTFS 元数据。简化做法是先用 FSCTL_GET_RETRIEVAL_POINTERS 通过正常文件句柄拿到簇号，再切到卷句柄写。

检测点在卷句柄：谁打开了 \\.\C:、谁在调 FSCTL_GET_RETRIEVAL_POINTERS、有没有非文件路径的写操作。部分 EDR 会在卷设备上监控 IRP_MJ_CREATE，但拿到的只是"有人打开了卷"，没有扇区级语义。

\\.\PhysicalDrive0 比卷句柄更底层，连分区都不管，误伤自己的风险也更高。

8.2 内存映射写入

CreateFileMapping 加 MapViewOfFile，改完再 FlushViewOfFile。写入由内存管理器在刷脏页时发出，形态是分页 I/O，IRQL 可能到 DISPATCH_LEVEL，minifilter 的回调在这种上下文里跑不了。很多 EDR 干脆跳过这类写入。

检测要落到映射动作：IRP_MJ_ACQUIRE_FOR_SECTION_SYNCHRONIZATION 能看到文件被映射，结合发起进程和后续执行行为判断。一个只读文档被映射之后紧接着加载模块，就不正常。

8.3 备用数据流

C:\temp\readme.txt:payload.exe。数据写在 payload.exe 这个流里，主文件看起来还是普通文本。minifilter 能查到完整名字（含流名），但规则只按扩展名匹配的 EDR 会漏。

检测靠枚举流：FindFirstStreamW、NtQueryInformationFile 的 FileStreamInformation，或者直接解析 MFT。文件大小和实际占用对不上，也是一个线索。

8.4 加密与分片

payload 用 XOR、AES 分段存，运行时读出来解密到内存。落地文件是密文，静态扫描看不到 PE 头、字符串、导入表。

检测只能靠熵和上下文：高熵文件、进程读取后分配可执行内存、随后外联，这几件事凑在一起才说明问题。单独一个高熵文件可能是压缩包、是图片，说明不了什么。

8.5 借合法进程写文件

certutil -urlcache -f、bitsadmin /transfer、expand、tar、curl 都能下载并写文件，进程是签过名的系统工具。minifilter 看到的是合法进程在写文件，规则只看进程签名就会放行。

判断点转到命令行、目标路径、父子关系。一个由 Office 拉起的 certutil 去下载 exe，和用户自己在命令行执行，完全是两回事。

8.6 抢在扫描之前执行

写完文件不关句柄，直接以执行方式打开并运行。CLEANUP 扫描还没触发，代码已经跑起来了。这类行为在 minifilter 侧表现为"写句柄没关，紧接着出现带执行意图的创建"，可以关联出来。

9. 一条完整的文件链

1. 下载
   powershell.exe 通过 HTTP 拉取文件
   网络事件：外联，进程是 powershell

2. 落地
   写入 C:\Users\Public\a.dat
   文件事件：创建 + 写入，进程 powershell，路径在用户目录

3. 关闭
   关闭句柄，CLEANUP 触发
   文件事件：关闭时扫描，内容是密文，静态规则不命中

4. 执行
   rundll32.exe 读取 a.dat，解密后在内存运行
   进程/镜像事件：rundll32 启动，内存中出现私有可执行页

5. 持久化
   写 Run 键
   注册表事件：写入者 rundll32，值指向用户目录

6. 横向
   在远端创建 PSEXESVC 服务，连 \\.\pipe\PSEXESVC
   管道事件：服务进程创建管道，客户端来自内网另一台机器

每一步都落在不同传感器上。第 3 步扫描没命中，不代表链条断了，第 4、5、6 步的行为足够把风险补回来。EDR 的告警通常也来自这样的组合，而不是单条文件事件。

10. 三类传感器的分工

传感器覆盖代价主要盲区
用户态 HookAPI 参数、调用上下文低直接系统调用、Unhook
内核回调进程、线程、镜像、注册表事件中看不到文件内容、事件字段可伪造
微筛选器文件创建、写入、改名、删除、命名管道高直接卷访问、内存映射写入、被卸载

内核回调回答"发生了什么"，微筛选器回答"文件里是什么、管道里过了什么"。两者都绕不过内核层的破坏：驱动被卸载、回调被摘除，上面这些传感器就一起失效。

11. 重点速记

  • 微筛选器是向 FltMgr 注册的文件系统过滤驱动，altitude 决定它在文件栈里的位置，号段大的先看到请求。
  • 实例按卷挂载，InstanceSetup 可以拒绝某个卷；上下文用来在同一个文件对象的多次回调之间共享状态。
  • pre 回调能放行、完成或拒绝，post 只能观察。文件内容拦截全在 pre。
  • 文件名要单独查询，FltGetFileNameInformation 受 IRQL 和文件状态限制，查不到时要有降级方案。
  • 缓存写入的数据不在回调缓冲区里，完整内容通常等 CLEANUP 再读。
  • 命名管道是 NPFS 上的文件对象，创建和连接都表现为 IRP_MJ_CREATE，管道名、创建者、客户端来源是三个主要判据。
  • 卸载防护靠四层：驱动拒绝停止、PPL 与 ELAM、文件自保护和互相守护；对抗手段集中在 BYOVD 改内核、改服务配置和阻断回传。
  • 绕过文件监测的路径：直接卷访问、内存映射写入、备用数据流、加密分片、借签名进程写文件、抢在扫描前执行。
  • 检测要把文件、管道、进程、镜像、注册表、网络事件串起来看，单条事件的信息量很小。

微筛选器看到的是磁盘上的字节变化和管道里流过的数据。字节为什么变、数据从哪来、变了之后拿去做什么，它答不了。
