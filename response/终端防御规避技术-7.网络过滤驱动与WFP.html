终端防御规避技术-7.网络过滤驱动与WFP

卷卷原创2026/11/1大约 11 分钟应急响应应急响应EDR终端防御与规避免杀网络过滤驱动WFPNDIS

内存、文件、注册表都讲完了，还剩一条通道没碰：网线。恶意程序要回连、要横向、要外传，最终都得经过网卡。EDR 在终端上盯这条通道有两种做法，一种是在网络驱动栈里插一层看包，另一种是走 Windows 过滤平台（WFP）看连接决策。这一章把这两条路讲清楚，顺带说明网络侧 NIDS 的位置和局限。

一、网络监控的两个位置

网络侧：NIDS

NIDS 是网络入侵检测系统，部署在交换机镜像口或者网关旁边，拿到的是整段网络的原始流量，用规则和协议解析做匹配，Snort、Suricata 都属于这一类。它看得到跨主机的东西：谁在扫内网、谁在跟陌生域名通信、哪台机器在往外传数据。

它的短板也很直接：加密。TLS 一普及，内容看不见，只能看目的 IP、端口、证书、包长和时序。另一个短板是归属，旁路流量里只有 IP 和端口，要知道是哪个进程发的，得再查终端上的连接表，或者结合 DHCP、登录日志去拼。

终端侧：驱动栈里的过滤

EDR 装在主机上，能在网络驱动栈里插入自己的检查点。和 NIDS 比，它天然知道"哪个进程发起的连接"，因为连接请求是从本机某个进程的句柄发出来的。代价是只能看到本机的流量，跨主机的行为得靠多台终端的日志汇聚。

书里把终端网络传感器归成两类：挂在 NDIS 层的包过滤驱动，和挂在 WFP 层的连接过滤。前者看到的是帧，后者看到的是连接决策，还带着进程上下文。这两个位置也是攻击者做网络规避时最先研究的地方。

二、NDIS：网卡和协议栈之间的三层

NDIS 是网络驱动接口规范，Windows 的网络驱动都按这个模型写。从上往下看，一条网线上的数据要穿过三层驱动：

应用
  WinSock / socket
    v
协议驱动（protocol driver，典型就是 TCP/IP）
    v
轻量过滤器（LWF，lightweight filter，可以叠好几层）
    v
小端口驱动（miniport driver，直接管网卡）
    v
网卡

对应的就是常说的"小端口、协议、过滤器中间层"：

  • 小端口驱动（miniport）：直接跟网卡硬件打交道，负责收发。可以理解成公司门口的收发室，快递进来出去都从这儿过。
  • 协议驱动（protocol）：实现 TCP/IP 这类协议，把帧拆成包、把包拼成流。是分拣员，负责把包裹拆开归类。
  • 过滤驱动（filter）：夹在协议和小端口之间的一层，能看到每一个进出网卡的帧，可以检查、修改、丢弃。是安检台，站在收发室和分拣员中间，谁的包裹都得过一遍。

老一点的模型里还有中间层驱动（IM driver），能同时挂多个协议，现在多数场景换成轻量过滤器。过滤器可以叠多层，安装时登记的绑定顺序决定谁在上谁在下，顺序写死，和微筛选器的 altitude 不一样。

这个位置的局限

NDIS 过滤器看到的是以太网帧和 IP 包，拿到的身份信息是 IP 和端口，不知道是哪个进程。它也不处理回环流量，本机进程之间走 localhost 的连接根本不经过网卡，过滤器看不到。加上加密以后，内容也读不出来。

这就是为什么后来的产品往 WFP 走：WFP 在连接建立的决策点上就能拿到发起进程的 ID。

三、WFP：Windows 过滤平台

WFP 全称 Windows Filtering Platform，微软从 Vista 开始提供的网络过滤框架。Windows 自带的防火墙就是架在它上面的，第三方 EDR 的网络传感器也大多挂在这里。

架构

用户态
  EDR 服务 / 防火墙管理界面
    | FwpmEngineOpen0、FwpmFilterAdd0（经 RPC 到 BFE）
    v
  BFE（Base Filtering Engine，基础过滤引擎服务）
    | 管理过滤器、子层、提供者、callout 注册信息
    v
内核
  WFP 过滤引擎
    层（layer）
      ALE_AUTH_CONNECT        出站连接建立前的授权
      ALE_AUTH_RECV_ACCEPT    入站连接接受前的授权
      ALE_FLOW_ESTABLISHED    连接建立后
      INBOUND_TRANSPORT       入站传输层
      OUTBOUND_TRANSPORT      出站传输层
      STREAM                  流数据
      DATAGRAM_DATA           数据报
    每个层上按 weight 排序过滤器
    动作：permit / block / callout
    callout 驱动（EDR 的网络传感器）
    v
  TCP/IP 驱动 → NDIS 轻量过滤器 → 网卡小端口 → 网卡

几个部件各管一摊：

  • 过滤引擎：内核里的执行体，按层和权重把每个连接、每个包送进对应的过滤器。
  • 层（layer）：框架预定义的检查点。连接从建立到断开，会依次经过授权层、建立层、传输层、流层，每个层都埋着钩子。
  • 子层（sublayer）：层下面的分组，用来给不同厂商的过滤器分优先级，EDR 的子层权重通常设得比系统防火墙高，保证先看到。
  • 过滤器（filter）：一条规则，包含匹配条件、动作、权重、所属子层。
  • callout：过滤器可以指定"把请求交给某个驱动函数处理"，这个驱动就是 callout 驱动。EDR 的检测逻辑基本都在 callout 的 classify 函数里。
  • 提供者（provider）：注册这些对象的厂商身份，也是用 GUID 标识。

callout 的返回值有三种：放行（permit）、阻断（block）、继续（continue，交给下一个过滤器）。除了看连接，callout 还能做流检测（FwpsStream* 系列接口）和包注入（FwpsInject*），前者用来在连接里读数据，后者用来重放或干扰。

权重和顺序

WFP 里过滤器按 weight 从大到小执行，权重高的先看到请求。系统防火墙、第三方 EDR、组策略下发的规则都在同一个层里排队，靠权重和子层区分先后。这个顺序是 WFP 的核心设计，也是攻击者研究绕过时要算的东西：如果 EDR 的过滤器权重比某个放行规则低，那条放行规则先放过去，后面的检查就没机会了。

门槛

写 WFP callout 驱动不需要 MVI、不需要 ELAM、不需要 PPL-AM，普通 WHQL 签名的内核驱动就能注册。这一点和 minifilter、Cm 回调一样，是没有 AM 资质的厂商也能做网络监控的原因。

四、GUID 是什么

GUID 全称 Globally Unique Identifier，全局唯一标识符，128 位，写成 8-4-4-4-12 的十六进制：

{22FB2CD6-0E7B-422B-A0C7-2FAD1FD0E716}

生成方式有 CoCreateGuid、UuidCreate，命令行 uuidgen，PowerShell 里 [guid]::NewGuid()。版本 4 的 GUID 大部分位是随机数，重复概率低到可以忽略。

WFP 里所有对象都用 GUID 认身份：提供者、子层、层、callout、每一条过滤器，各有一个 key。系统预定义的层有固定常量，比如 FWPM_LAYER_ALE_AUTH_CONNECT_V4，头文件里就是一个写死的 GUID。厂商自己注册的 callout 和过滤器也用固定 GUID，这样重启之后还能按同一个身份找到自己写进去的规则。

ETW 的提供者也用 GUID 标识，下一章会反复用到。记住一点：GUID 只是名字，不带语义，看到一串 GUID 要知道它对应哪个组件，得查文档或查注册信息。

五、用网络过滤器盯住攻击行为

网络传感器看的不是文件内容，是"谁在什么时候跟谁说了多少话"。把连接的五元组、发起进程、字节数、时间间隔放在一起，能还原出大部分攻击阶段。

战术网络侧特征观察点
C2 回连固定间隔的小包往返，带抖动同一进程周期性外联、目标域名新注册、TLS 指纹不常见
DNS 隧道超长域名、高熵标签、大量 TXT 查询查询频率、域名结构、解析失败率
横向移动445 SMB、135 RPC、5985 WinRM、3389 RDP发起进程不是运维工具、目标是一次性批量 IP
凭据攻击88 Kerberos、NTLM 认证异常非域控进程发起认证、认证失败集中
数据外传出站字节远大于入站非工作时段、目的地是云存储或陌生主机
内网扫描大量短连接、大量失败单位时间内目标 IP 和端口数量
隧道代理非常规端口承载 TLS、链路跳数异常端口与协议不匹配、证书链可疑
下载载荷小请求换大响应浏览器以外的进程发起 HTTP、文件类型与进程不匹配

关键在进程归属

只有五元组，一条连接和一个 IP 地址没有区别。ALE 授权层能看到发起连接的进程 ID，这才是终端侧网络监控比 NIDS 值钱的地方。同一个 443 连接，来自 msedge.exe 和来自 rundll32.exe，风险完全不同。

关联比单点重要

一次外联本身说明不了什么。真正有用的是把网络事件和进程事件、文件事件、注册表事件放在一条时间线上：winword.exe 拉起 powershell.exe，powershell.exe 从临时目录加载一个 DLL，这个 DLL 每 30 秒连一次新域名。四件事单看都普通，串起来就是一条完整的链。

六、网络侧的规避

加密

最彻底的一招是把所有流量套进 TLS，用合法证书，走标准 443。内容检测直接失效，检测只能退回元数据：目的域名、证书签发者、证书年龄、JA3/JA4 指纹、包长分布、连接周期。

域前置

TLS 的 SNI 写成一个合法的大域名，流量实际落到 CDN 后面的另一个服务。中间设备看到的是合法域名，终端看到的连接目标是 CDN 节点。检测要靠证书与 SNI 的对应关系、CDN 节点的异常使用、以及进程行为。

借合法通道

把 C2 塞进 OneDrive、GitHub、Slack、邮件、Teams 这类服务，域名和证书都是真的，流量混在正常业务里。这类通道的特点是协议正常、域名可信、频率低。

降频与伪装

慢速 beacon，几小时一次，带随机抖动；把请求做成正常 HTTP 页面访问；用 WebSocket 长连接；分片传输、压缩、隐写。所有手段都指向同一个目标：让流量在统计上不像恶意流量。

换协议、换路径

DNS over HTTPS 把查询藏进 443，DNS 监控看不到明文域名；内网横向改用 SMB 命名管道，避免新建外联；用签名进程发起连接，比如 certutil、bitsadmin、mshta，让进程谱系看起来正常。

检测侧的应对

网络侧没法靠解密，就得靠行为：首次出现的域名、证书签发时间很短、进程不该发这种连接、出站入站字节比失衡、连接周期过于规律。这些指标不需要看内容，也不怕 TLS。

七、几类网络传感器对照

传感器看到什么进程归属加密流量位置
NIDS原始包、协议字段需要关联其他日志只看元数据网络侧旁路
NDIS 过滤器帧、IP 包弱，需要额外查询只看元数据终端内核
WFP callout连接决策、五元组强，ALE 层直接带 PID只看元数据终端内核
ETW 网络事件连接建立、收发字节强只看元数据终端
网关代理日志域名、URL、证书弱代理终止 TLS 时可解密网关

从 NDIS 到 WFP，变化的是能看到多少上下文；从终端到 NIDS，变化的是覆盖范围。真实的产品通常几层一起用，靠关联而不是靠单点。

八、重点速记

  • NIDS 在旁路看整段流量，覆盖面广，但加密后只能看元数据，进程归属要靠关联。
  • NDIS 分三层：小端口管硬件、协议驱动实现 TCP/IP、过滤器夹在中间看帧。过滤器能改包丢包，但拿不到进程，也看不到回环流量。
  • WFP 是微软的网络过滤框架，Windows 防火墙就架在上面。核心部件是过滤引擎、层、子层、过滤器、callout、提供者。
  • 层是预定义的检查点，ALE 授权层能看到发起连接的进程 ID，这是终端网络监控的关键优势。
  • 过滤器按 weight 从大到小执行，权重和子层决定谁先看到请求。
  • WFP 对象全用 GUID 标识，系统层有固定常量，厂商注册的 callout 和过滤器也用固定 GUID 以便持久化。
  • 网络检测靠五元组加进程上下文加时间序列，单条连接说明不了问题。
  • 规避网络检测的主力是加密、域前置、借合法云服务、降频伪装，检测退回到元数据和行为。
