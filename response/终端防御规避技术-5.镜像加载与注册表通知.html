终端防御规避技术-5.镜像加载与注册表通知

卷卷原创2026/10/28大约 18 分钟应急响应应急响应EDR终端防御与规避免杀镜像加载通知注册表通知KAPC

进程创建通知记录"谁启动了程序"，镜像加载通知记录"程序后来又装了什么"。一个看进程对象，一个看映像映射。这一章还牵出两件容易混在一起的事：注册表通知管配置面的改动，APC 管执行时机，而镜像加载通知恰好能给 APC 注入提供一个稳定的触发点。

1. 镜像加载通知的原理

1.1 映像必须先变成 section

PE 文件躺在磁盘上只是一串字节。要让 CPU 执行，得先由内核把它映射成一段可执行内存，这段内存来自 image section。

文件系统上的 PE
  | NtCreateSection(..., SEC_IMAGE, ...)
  v
Section 对象（内核里的 _SECTION）
  | NtMapViewOfSection
  v
目标进程地址空间：ImageBase + ImageSize
  | 加载器处理导入表、重定位、TLS、异常表
  v
DllMain / 入口点

SEC_IMAGE 是关键参数。它告诉内核按 PE 格式解析这个文件，而不是当成一块普通数据。只有 image section 被映射进进程时，内核才会走通知链；普通数据 section 不会。

1.2 通知链在哪一环被调用

内核维护一张全局的镜像通知回调表。驱动调用 PsSetLoadImageNotifyRoutine，自己的函数挂到表上。每次有 image section 被映射，内存管理器在映射完成、入口点执行之前遍历这张表，逐个调用。

NtMapViewOfSection(SEC_IMAGE)
  v
内存管理器建立映像映射
  v
遍历全局镜像通知链
  +--> EDR 回调 1：取路径、签名、FileObject
  +--> EDR 回调 2：记事件、送队列
  +--> 其他驱动回调
  v
返回用户态，加载器继续初始化
  v
DllMain / 入口点执行

回调在发起加载的线程上下文里执行，运行在 PASSIVE_LEVEL。它不能阻塞，不能等 I/O，也不能把这次加载取消——这个接口没有返回值，通知只是告知，不是审批。

为什么这个时机好用

映像已经映射，路径、大小、FileObject 都在手里；初始化代码还没跑，EDR 还有机会做后续动作。真要阻断，通常不在这里做，而是在创建进程、创建文件那一步拦，或者加载后立刻挂起、终止进程。

回调之间互不感知

多个安全产品各自注册，回调按注册顺序执行。前一个回调做了什么、有没有失败，后一个看不到。装两套 EDR 时，同一个 DLL 加载会被记录两遍，两套规则各自判断，互不影响。

1.3 回调拿到的三个参数

VOID OnImageLoad(PUNICODE_STRING FullImageName, HANDLE ProcessId, PIMAGE_INFO ImageInfo);
参数/字段含义
FullImageName映像路径，可能是 DOS 路径、设备路径或空值
ProcessId载入映像的进程；内核驱动为 0
ImageBase映像在目标地址空间里的基址
ImageSize映像大小
SystemModeImage1 表示内核驱动，0 表示用户态映像
ExtendedInfo仅 Ex 注册时有效，含 FileObject、ImageSignatureLevel、ImageSignatureType

FileObject 比名字可靠。拿它查签名、算哈希、取最终路径，都能绕开字符串层面的伪装。

FullImageName 的三种形态

正常用户态加载给出 C:\Windows\System32\amsi.dll 这样的 DOS 路径。某些内核组件看到的是设备路径，形如 \Device\HarddiskVolume3\Windows\System32\xxx.sys。少数情况下它是空指针，只能从 FileObject 反推。规则只写死 DOS 路径，前两种都会漏。

签名级别不等于安全

ImageSignatureLevel 能区分微软签名、WHQL、Authenticode、未签名。签名合法只说明文件没被改过，说明不了它有没有漏洞。BYOVD 用的驱动全都带合法签名。

1.4 两种注册方式

NTSTATUS PsSetLoadImageNotifyRoutine(PSEX_LOAD_IMAGE_NOTIFY_ROUTINE Notify);
NTSTATUS PsSetLoadImageNotifyRoutineEx(PSEX_LOAD_IMAGE_NOTIFY_ROUTINE Notify, ULONG Flags);

Ex 版本支持 PS_IMAGE_NOTIFY_CONFLICTING_ARCHITECTURE 标志，用来接收与系统架构不一致的映像通知。普通版本覆盖大多数场景，是否需要这个标志取决于产品要覆盖的范围。

注销用 PsRemoveLoadImageNotifyRoutine(Notify)，必须在驱动卸载之前完成，回调还挂在链上就卸载驱动会直接蓝屏。

1.5 和进程创建通知的分工

通知回答的问题触发时机主要字段
进程创建谁启动了程序进程对象建立后、主线程执行前映像路径、命令行、父进程
镜像加载程序后来又装了什么image section 映射后、入口点执行前模块路径、大小、签名、FileObject
线程创建谁开始跑了线程真正开始执行时起始地址、所属进程

三条放在一起，才能还原"谁启动了什么、装了什么、什么时候开始跑"。

2. 哪些加载不触发通知

行为是否触发原因
LoadLibrary / LdrLoadDll是走 image section 映射
进程启动主映像是内核映射 EXE 的 image section
驱动加载是系统模式映像，ProcessId 为 0
反射式加载、手动映射否自己分配内存拷贝，没有 image section
Assembly.Load(byte[])否从字节数组加载，不产生映像映射
映射非 SEC_IMAGE 的 section否数据映射，内核不当作映像
重复加载同一个 DLL否只增加引用计数，没有新的映射
模块踩踏加载时触发，改写时不触发通知只覆盖映射那一刻
进程空心化创建时触发，替换后不触发主映像通知照常发出，之后的内容变化看不到

最后三行是重点。通知本身没错，错在它只覆盖一个瞬间。

重复加载为什么不算一次

LoadLibrary 第二次指向同一个 DLL，加载器发现模块已在进程里，只把引用计数加一，不会重新映射。攻击者可以利用这一点：先让目标进程加载某个合法 DLL，之后自己用同一路径再加载，通知只响第一次。

3. 隧道加载：把加载动作借给可信进程

镜像通知记录的是"哪个进程加载了哪个模块"。如果加载动作不是由攻击者进程发起，而是由 rundll32.exe 发起，记录里就是一个签名的系统程序加载了一个 DLL。

攻击者控制端
  | 1. 投放 DLL 到磁盘
  | 2. 下发命令：用代理进程加载哪个 DLL、调哪个导出函数、传什么参数
  v
代理进程（签名合法：rundll32 / regsvr32 / dllhost / msiexec）
  | LoadLibrary(目标 DLL)
  | GetProcAddress(导出函数)
  | 调用
  v
恶意 DLL
  | 3. 执行载荷
  | 4. 回连 C2
  v
攻击者控制端

这条链路里，镜像加载通知看到的是代理进程加载 DLL：父进程是 explorer 或者任务计划，签名有效，进程名在系统白名单里。攻击者自己的 loader 可能根本没有加载记录，或者只加载了系统 DLL。

常见宿主

rundll32.exe C:\Users\Public\up.dll,Start 是最直接的一种。regsvr32 /s 会调用 DllRegisterServer。COM 激活走 dllhost.exe，注册表里写一个 CLSID，再用 CoCreateInstance 拉起。msiexec、wscript、mshta 也能承担类似角色。

为什么叫隧道

动作借道可信进程，像从别人的门进出。通知、进程树、签名检查看到的都是那个门，攻击者的进程藏在后面。

检测点

代理进程的命令行是最直接的一条：rundll32 加载用户目录里的 DLL，导出函数名不像常规用法（不是 Control_RunDLL、不是系统 DLL），就值得查。DLL 的路径和签名是第二条。代理进程加载完之后立刻外联，是第三条。父子关系也能补一刀：Office 进程拉起的 rundll32，和用户手动执行不是一回事。

4. 用镜像加载通知触发 KAPC 注入

4.1 APC 是什么

APC（Asynchronous Procedure Call，异步过程调用）是线程级的"等会儿再执行"。每个线程有 APC 队列，插进去的函数不会立刻跑，要等线程回到一个合适的状态才执行。

分两类。用户态 APC 由 QueueUserAPC 插入，线程进入可警告等待（alertable wait，比如 SleepEx、WaitForSingleObjectEx）时才执行。Early Bird 用的就是这一类。内核态 APC 由驱动插入，线程下一次从内核返回、IRQL 降到 APC_LEVEL 以下时执行；如果 ApcMode 设成 UserMode，APC 里的主逻辑会在线程返回用户态时以用户代码的身份执行。

APC 队列属于线程，不属于进程

同一个进程里，往哪个线程排队，决定了代码什么时候跑。目标线程如果一直在忙，APC 就一直等；线程如果退出，队列里的 APC 会被 rundown 例程清理。

4.2 KAPC 是什么

KAPC 是内核里描述一次内核 APC 的结构（wdm.h 里的 _KAPC，下面是节选）：

typedef struct _KAPC {
    PKTHREAD Thread;                 // 目标线程
    LIST_ENTRY ApcListEntry;         // 挂到线程的 APC 队列
    PKKERNEL_ROUTINE KernelRoutine;  // 内核态入口
    PKRUNDOWN_ROUTINE RundownRoutine; // 线程退出时的清理
    PKNORMAL_ROUTINE NormalRoutine;  // 主逻辑
    PVOID NormalContext;
    PVOID SystemArgument1;
    PVOID SystemArgument2;
    CCHAR ApcStateIndex;
    KPROCESSOR_MODE ApcMode;         // KernelMode 或 UserMode
    BOOLEAN Inserted;
} KAPC, *PKAPC;

KernelRoutine 永远在内核态跑，负责收尾、释放资源。NormalRoutine 才是真正要执行的代码，跑在哪个态由 ApcMode 决定。NormalContext 和两个 SystemArgument 是传参用的。

插入队列的两个函数

KeInitializeApc 填结构，KeInsertQueueApc 把它挂到目标线程的队列上。插入失败（返回 FALSE）通常是因为这个 KAPC 已经在队列里了，同一个结构不能重复插。

4.3 一次完整的 KAPC 注入

// 1. 找到目标进程和线程
PsLookupProcessByProcessId(pid, &process);
PsLookupThreadByThreadId(tid, &thread);

// 2. 在目标地址空间里准备 shellcode
KeStackAttachProcess(process, &apcState);
ZwAllocateVirtualMemory(...);      // 分配可执行内存
memcpy(...);                       // 写入 shellcode
KeUnstackDetachProcess(&apcState);

// 3. 构造并排队
KeInitializeApc(&kapc, thread, OriginalApcEnvironment,
                KernelRoutine, NULL,
                (PKNORMAL_ROUTINE)shellcode, UserMode, NULL);
KeInsertQueueApc(&kapc, NULL, NULL, 0);

三步里，第二步最容易被察觉：跨进程分配可执行内存、写入未知内容。第三步是纯粹的队列操作，用户态看不到任何事件。

KAPC 注入必须有驱动

KeInitializeApc、KeInsertQueueApc 都是内核导出函数，用户态调不到。这也是为什么这类技术总和 BYOVD 一起出现：攻击者需要一个能执行任意内核代码的入口。

4.4 镜像加载通知怎么成为触发器

驱动注册了镜像加载通知之后，回调会在"目标进程正在加载映像"的上下文里执行。这个上下文对注入很友好。

目标进程加载任意映像
  v
内存管理器调用通知链
  v
攻击者驱动回调（运行在目标进程上下文）
  | PsGetCurrentProcess() -> 目标进程
  | PsGetCurrentThread()  -> 正在加载映像的线程
  | 判断映像名/进程名是否命中
  v
在目标进程地址空间写 shellcode
  v
KeInsertQueueApc 到当前线程
  v
回调返回，线程继续初始化
  v
线程返回用户态，APC 执行 shellcode

用镜像通知做触发点，省掉了两件事：不用 OpenProcess 拿句柄，不用 KeStackAttachProcess 切换地址空间。回调本来就在目标进程里跑，PsGetCurrentProcess() 直接就是目标。APC 也能直接排给当前线程，不用遍历线程列表。

触发条件的挑法

回调可以对所有映像加载都触发，也可以只在特定进程加载特定 DLL 时动手。后者更隐蔽：等目标进程加载 amsi.dll、ole32.dll 这类几乎一定会加载的模块，命中概率高，时间点也自然。

代价

驱动加载本身会触发镜像通知（SystemModeImage 为 1），还会被驱动签名策略、漏洞驱动黑名单记录。注入成功之后，APC 执行的代码位于私有可执行页，不在任何已知模块里，内存扫描能看出来。

4.5 怎么防

层面手段作用
驱动加载驱动签名强制、HVCI、WDAC、漏洞驱动黑名单没有驱动，KAPC 注入无从谈起
权限管控 SeLoadDriverPrivilege减少能加载驱动的人
回调链EDR 自保护、驱动互相守护防止已注册的回调被摘掉
执行内存扫描、线程栈回溯、私有可执行页检查发现 APC 执行后的 shellcode
用户态 APC对象回调限制 THREAD_SET_CONTEXT、监控 QueueUserAPC拦住 Early Bird 这类用户态变体

没有事件可看

APC 插入这个动作本身不对用户态暴露，ETW 里也没有对应事件。防守方只能从两头看：驱动能不能加载进来，执行后内存里有没有异常页。中间那一步是黑的。

5. 注册表通知的原理

5.1 蜂巢与配置管理器

注册表是一个分层数据库。每个蜂巢（hive）对应磁盘上的一个文件，文件里是一堆 cell，键和值都是 cell。系统启动时把蜂巢加载进内存，修改先落到内存和日志，之后延迟写回磁盘。

配置管理器（Configuration Manager，CM）负责解析路径、缓存键、处理事务和日志。用户态的 RegSetValueEx、内核里的 ZwSetValueKey，最后都进 CM。

5.2 回调怎么挂上去

NTSTATUS CmRegisterCallbackEx(
    PEX_CALLBACK_FUNCTION Function,
    PCUNICODE_STRING Altitude,
    PVOID Driver,
    PVOID Context,
    PLARGE_INTEGER Cookie,
    PVOID Reserved);

NTSTATUS RegistryCallback(PVOID Context, PVOID Argument1, PVOID Argument2);

Argument1 是 REG_NOTIFY_CLASS，说明这次是哪个操作、是操作前还是操作后；Argument2 指向该操作对应的结构体，里面有键路径、值名、值数据、调用者信息。

注册要填 altitude，取值由微软分配。多个产品同时注册时，同一操作上的回调按 altitude 排序，谁先看到、谁能先阻断由这个值决定。

pre 能拦，post 只能看

pre 回调返回非成功状态码（比如 STATUS_ACCESS_DENIED），这次注册表操作就失败，调用方拿到错误。post 回调运行时，操作已经完成，只能记录结果。

运行环境

回调在发起操作的线程上下文里执行，不能阻塞，不能等 I/O，也不能去调用可能重入的注册表接口。注册表操作极其频繁，系统启动时每秒可能上千次，回调里做重活会把整机拖慢。

覆盖范围

只覆盖经过 CM 的操作。用户态 API、内核里的 Zw* 都算；直接改蜂巢文件、绕过 CM 操作内存里的 hive，不算。

8. 规避注册表回调

8.1 离线修改蜂巢

蜂巢就是磁盘上的文件：

蜂巢文件路径
HKLM\SYSTEMC:\Windows\System32\config\SYSTEM
HKLM\SOFTWAREC:\Windows\System32\config\SOFTWARE
HKLM\SAMC:\Windows\System32\config\SAM
HKLM\SECURITYC:\Windows\System32\config\SECURITY
用户配置C:\Users\<用户>\NTUSER.DAT

系统运行时这些文件被独占。要改，得用 WinPE 或第二套系统挂载磁盘，在 EDR 没运行的环境里动手。改完重启，配置生效，全程没有一条回调记录。

reg load 加载其他用户的 NTUSER.DAT 仍然经过 CM，能看到 RegNtPreLoadKey 和后续写入，所以它不算离线修改，只是换了操作对象。

8.2 整份替换：RestoreKey 与 ReplaceKey

RegSaveKey 导出一份蜂巢，改完再用 RegRestoreKey 覆盖目标键。逐条写值不会各自触发 RegNtPreSetValueKey，回调里出现的是恢复这个动作。规则只按"写值"匹配的 EDR 会漏。

RegReplaceKey 更进一步，它把蜂巢文件换掉，下次启动时生效。回调只看到一次替换请求，看不到替换后里面有什么。

这两个 API 需要特权：RegSaveKey 要 SeBackupPrivilege，RegRestoreKey 和 RegReplaceKey 要 SeRestorePrivilege。管理员默认持有，普通用户拿不到。

8.3 WOW64 重定向

32 位进程写 HKLM\SOFTWARE\...，会被重定向到 HKLM\SOFTWARE\Wow6432Node\...。规则只写原生路径，就会漏掉 32 位进程写进来的值。用户侧的 HKCU\Software\Classes 也有对应的 Wow6432Node 分支，COM 劫持经常踩这里。

8.4 换位置与不用注册表

持久化位置很多，名单覆盖不全。相对冷门的有 Print\Monitors、NetSh helper、SilentProcessExit、BootExecute、AppCertDlls、屏幕保护程序。位置越冷门，规则越可能缺。

另一条路是根本不用注册表：计划任务（XML 文件）、WMI 事件订阅（OBJECTS.DATA 仓库）、启动文件夹、服务二进制、DLL 侧加载。这些不产生注册表写入，得靠文件、WMI、服务事件去发现。

8.5 内核层

摘掉 EDR 的注册表回调、卸载驱动、用漏洞驱动直接改 hive。需要内核权限，门槛高，成功之后所有注册表监控一起失效。这和第四章"摘对象回调"是同一个思路。

8.6 借安装程序与系统组件

msiexec 安装 MSI、Windows Update 写配置、组策略刷新，都会往敏感键里写值。这些进程签名合法、行为固定，白名单绕不开。攻击者把恶意配置塞进一个 MSI，或伪造组策略文件，回调里看到的写入者是可信组件。

判断点转到值的来源和路径：MSI 从用户目录安装、组策略文件时间戳异常、写入的值指向临时目录。

9. 一条链路上的三类通知

1. 写启动项
   HKLM\...\Run\Updater = rundll32.exe C:\Users\Public\up.dll,Start
   注册表通知：RegNtPreSetValueKey
   写入者：powershell.exe，值里带 rundll32 和用户目录

2. 重启后触发
   explorer.exe 读取 Run 键，创建 rundll32.exe
   进程创建通知：父进程 explorer.exe，命令行带 up.dll

3. 借代理加载
   rundll32.exe 加载 up.dll
   镜像加载通知：路径 C:\Users\Public\up.dll，无签名，宿主是系统程序

4. 读加密载荷
   up.dll 读取同目录 dat 文件，解密后在内存执行
   没有创建事件，没有映像加载，只能靠内存扫描和网络行为

四步里三类通知各管一段。第一步和第三步的异常都很明显，第二步要靠父子关系判断，第四步基本是空的。如果 loader 再用镜像通知触发的 KAPC 把代码塞进 explorer.exe，那第四步连进程创建都不会发生。

10. 重点速记

  • 镜像加载通知由 image section 映射触发，回调在映像已映射、入口点未执行之间运行，只能告知，不能阻断。
  • 手动映射、反射加载、Assembly.Load(byte[])、数据 section 都不触发通知；重复加载同一个 DLL 也不触发。
  • FullImageName 可能是设备路径或空值，FileObject 更可靠。
  • 隧道加载把动作借给签名进程，通知里看到的是代理进程，检测要看命令行、DLL 路径、签名和后续外联。
  • KAPC 是内核 APC，KeInitializeApc 填结构、KeInsertQueueApc 入队，ApcMode 设为 UserMode 时主逻辑在用户态执行。
  • 镜像通知的回调天然运行在目标进程上下文，省掉打开句柄和切换地址空间，是 KAPC 注入的顺手触发点；防守只能卡驱动加载和执行后的内存特征。
  • 注册表回调用 CmRegisterCallbackEx 注册，pre 能阻断，post 只能看，只覆盖经过 CM 的操作。
  • 注册表侧的绕过集中在四处：离线改蜂巢、RestoreKey/ReplaceKey 整份替换、WOW64 重定向、冷门位置或干脆不用注册表。

镜像通知看到的是"模块进来了"，注册表通知看到的是"配置被改了"。模块进来之后干什么、配置改完谁来读，这两件事都不在通知的视野里。
