现代攻击却大量走脚本：PowerShell 一行命令、Office 宏、wscript、mshta、.NET 动态编译。这些载荷可以完全不落盘，或者落盘的是编码后的一串字符，静态扫描看到一排 Base64 判断不了任何东西。AMSI 就是为这个缺口造的——在脚本真正执行之前，把明文内容截下来交给杀软看一眼。

## 一、脚本恶意软件的挑战

脚本的执行方式和 PE 完全不同。PE 有文件头、导入表、节表，扫描器有一堆结构可以分析；脚本是纯文本，由解释器逐段解析、编译成内部结构再执行。

常见载体：

- PowerShell：`-EncodedCommand`、下载后再 `Invoke-Expression`（IEX）执行。
- VBScript / JScript：由 `wscript.exe`、`cscript.exe` 解释。
- Office VBA 宏：打开文档即触发。
- WMI 脚本：通过 WMI 服务远程或本地执行。
- .NET 程序集：`Assembly.Load` 从字节数组直接加载，不落盘。
- mshta、regsvr32、rundll32 等白名单程序做代理执行。

共有两个特点，正好打在传统扫描的软肋上：

1. **文件不存在**。载荷在内存里生成，磁盘上没有可扫的对象。
2. **文件存在但看不懂**。内容是 Base64、XOR 或多层拼接，特征匹配不上。

所以需要的机制不是"再扫一遍文件"，而是：<mark>在解释器把脚本编译成可执行结构之前，把"将要执行的内容"截获，交给反恶意软件引擎判断</mark>。这就是 AMSI 的设计目标。

## 二、AMSI 是什么

AMSI 全称 Anti-Malware Scan Interface，Windows 自带的一套扫描接口。它不是杀软，是"客户端—接口—提供者"三方的一个约定。

三个角色：

- **客户端（Client）**：要执行脚本的应用。`powershell.exe`、`wscript.exe`、`mshta.exe`、Office、.NET 运行时都可能是。
- **接口（amsi.dll）**：提供 `AmsiInitialize`、`AmsiOpenSession`、`AmsiScanBuffer`、`AmsiScanString`、`AmsiCloseSession`、`AmsiUninitialize` 这几个导出函数。它负责把内容送进已注册的提供者。
- **提供者（Provider）**：杀软实现的 COM 组件，注册在：

```text
HKLM\SOFTWARE\Microsoft\AMSI\Providers\{GUID}
```

以 Windows Defender 为例，它的提供者 CLSID 通常是：

```text
{2781761E-28E0-4109-99FE-B9D127C57AFE}
```

具体值以本机注册表为准。装了第三方杀软时，这里会多出对应厂商的 GUID。

调用流程：

1. 进程启动，客户端调用 `AmsiInitialize(L"PowerShell", &ctx)`，拿到一个上下文。
2. 每次要执行一段内容前，先 `AmsiOpenSession(ctx, &session)`。
3. 把内容传进去：`AmsiScanBuffer(ctx, buffer, len, contentName, session, &result)`。
4. amsi.dll 把 buffer 交给提供者，提供者返回结果。
5. 客户端看结果决定是否执行，最后 `AmsiCloseSession`。

结果码只有几种：

| 结果 | 值 | 含义 |
|---|---|---|
| AMSI_RESULT_CLEAR | 0 | 干净 |
| AMSI_RESULT_NOT_DETECTED | 1 | 没检测到（不等于干净） |
| AMSI_RESULT_DETECTED | 0x8000（32768） | 判定为恶意 |

关键点：**AMSI 只负责"把内容送过去"，判断完全依赖提供者**。它不做 PE 解析、不做内存扫描，规则和情报都在杀软那一侧。AMSI 提供的是"检查点"，不是"检测能力"。

## 三、PowerShell 的 AMSI 实现

`powershell.exe` 启动时加载 `amsi.dll`，以 `"PowerShell"` 作为应用名初始化上下文。之后这些内容在编译成 AST（抽象语法树）之前都会经过 `AmsiScanBuffer`：

- 交互式输入。
- `-Command` 参数。
- `-EncodedCommand` 参数（Base64 先解码成明文再送扫）。
- 脚本文件的内容。
- `Invoke-Expression` 的字符串参数。

所以 `-enc` 并没有绕过 AMSI，它只是绕过了命令行审计。真正要躲的是扫描本身。

这里容易混的一点：AMSI 和脚本块日志（Script Block Logging）是两套独立机制。

| 机制 | 作用 | 通道 | 关闭影响 |
|---|---|---|---|
| AMSI | 执行前拦截 | amsi.dll + 杀软 provider | 脚本不再被扫 |
| Script Block Logging | 执行审计 | ETW `Microsoft-Windows-PowerShell` | 不留日志 |

关掉其中一个不影响另一个。防守方两套都开，攻击方才需要两套都处理。

正因为 PowerShell 是脚本攻击的主战场，它也是 AMSI 对抗的主战场：只要能在一个 PowerShell 进程里让 `AmsiScanBuffer` 失效，后续所有命令都不再被扫。

## 四、底层到底发生了什么

用安检做个类比：

```text
脚本内容
   |
   | 客户端（解释器）调用 AmsiScanBuffer
   v
amsi.dll（接口层）
   |
   | 按注册表找到 provider，加载其 COM DLL 到当前进程
   v
杀软 provider（判图的人）
   |
   | 返回 CLEAR / NOT_DETECTED / DETECTED
   v
客户端决定：继续执行 / 抛异常拒绝
```

几个容易被忽略的事实：

- `amsi.dll` 是**用户态 DLL**，每个进程各有一份。你在 A 进程里打补丁，对 B 进程毫无影响；要打就得在目标进程内部执行代码。
- provider 是 COM 组件，第一次扫描时才加载（延迟加载）。也就是说，<mark>杀软的 AMSI 检测逻辑跑在被扫进程里，不是跑在杀软自己的进程里</mark>。这给了攻击者"在同一个进程里改内存"的机会。
- 扫描结果会上报给杀软的服务或云端，形成事件。本地放过不等于没有记录，云端可能事后标记。
- 部分杀软会做完整性检查：比对 amsi.dll 在磁盘和内存中的字节，或者检测已知补丁的特征。

## 五、规避 AMSI

### 字符串混淆

最先要处理的不是 AMSI 本身，而是"绕过脚本会不会先被 AMSI 抓住"。如果脚本里明文写着 `AmsiScanBuffer`、`amsi.dll`、`VirtualProtect`、`AmsiUtils`，很可能在补丁生效之前就被判定为恶意工具。

所以第一步总是隐藏这些字符串：

- 拆分拼接：`"Am" + "si" + "ScanBuffer"`。
- 用字符码拼接：`[char]` 逐个拼。
- Base64 或自定义编码存储，运行时解码。
- 从资源、环境变量、注册表里取，不写在脚本正文。
- 用反射和动态解析去拿 P/Invoke 的函数地址，不写死导出名。

这一步属于元规避：不是为了骗过检测逻辑，而是为了让"准备绕过"这个动作本身不被提前发现。

### AMSI 修补

原理很直接：`AmsiScanBuffer` 开头几条指令负责校验参数、调用提供者。把入口改成"立刻返回一个非 DETECTED 的值"，后面所有扫描就都失效了。

步骤：

1. 拿到 `amsi.dll` 的模块基址（`GetModuleHandle` 或遍历 PEB 的模块链表）。
2. 解析导出表，找到 `AmsiScanBuffer` 的地址。
3. `VirtualProtect` 把目标内存改成可写。
4. 写入补丁字节。
5. 把内存保护属性恢复回去。

常见补丁形态：

- `xor eax, eax; ret`：返回 0，等于 CLEAR。
- `mov eax, 0x80070057; ret`：返回 E_INVALIDARG。解释器把"扫描失败"当成非致命错误，继续执行。这一种比返回 CLEAR 更稳，因为有些组件对 CLEAR 还有额外判断。
- 把前两个字节改成短跳 `EB`，跳到函数尾部的一条 `ret`，保留大部分原始字节。

C 形态大致是这样：

```c
FARPROC target = GetProcAddress(GetModuleHandleA("amsi.dll"), "AmsiScanBuffer");
DWORD old;
VirtualProtect(target, 0x20, PAGE_EXECUTE_READWRITE, &old);
memcpy(target, patch, sizeof(patch));   /* 例如 33 C0 C3：xor eax,eax; ret */
VirtualProtect(target, 0x20, old, &old);
```

PowerShell 还有一种更早期的"软关闭"，直接改运行时状态而不碰代码：

```powershell
$a = [Ref].Assembly.GetType('System.Management.Automation.AmsiUtils')
$f = $a.GetField('amsiInitFailed', 'NonPublic,Static')
$f.SetValue($null, $true)
```

把 `amsiInitFailed` 置为真，后续扫描直接被跳过。这个方法后来被微软修补，也被各家杀软列为特征，现在基本失效。但它体现的思路一直有效：<mark>不一定要改代码，改状态也行</mark>。

### 补丁绕过

杀软对 AMSI 的保护不止"看字节"，通常还有几层：

- 比对 amsi.dll 在磁盘与内存中的哈希。
- 检测已知补丁的特征字节，比如 `33 C0 C3` 出现在 `AmsiScanBuffer` 头部。
- 监控对 amsi.dll 的写操作（内核回调或 ETW）。
- 检查 `AmsiScanBuffer` 前几个字节是否被改成跳转。

补丁绕过就是针对这些检测做变形：

- **换等价指令**：`33 C0 C3`（xor eax,eax; ret）、`2B C0 C3`（sub eax,eax; ret）、`6A 00 58 C3`（push 0; pop rax; ret）、`B8 00 00 00 00 C3`（mov eax,0; ret）。返回值一样，字节不同。
- **改中间不改开头**：保留函数入口的完整字节，把调用 provider 的那条 `call` 改成 `nop`，完整性检查看到入口正常就放过。
- **延迟修补**：等 AMSI 完成首次扫描之后再改，避开启动期的检查窗口。
- **先恢复后修补**：执行完把原始字节写回去，缩小"被改"的时间窗。
- **换补丁位置**：不碰 `AmsiScanBuffer`，改它的调用点，或者去 hook provider 自己导出的扫描函数。
- **硬件断点**：在 `AmsiScanBuffer` 上设置 `Dr0` 断点，异常处理器里直接改返回值。内存字节从头到尾没变，专打字节完整性检查。
- **卸载再加载**：让 amsi.dll 从进程里卸载并重新映射，绕过对"已改内存"的检测。要处理句柄和引用计数，实现成本高。

再往上还有 provider 层的对抗：让 provider 加载失败（破坏注册表项、DLL 劫持、权限阻断）。AMSI 找不到提供者时返回 `AMSI_RESULT_NOT_DETECTED`，扫描等于空转。这类手法需要管理员权限，会影响整机的安全产品，痕迹比进程内 patch 重得多。

## 六、这个模型的边界

- AMSI 只覆盖"愿意调用它的客户端"。原生 C 程序、自己实现的解释器、不调用 AMSI 的第三方运行时，完全在覆盖之外。
- AMSI 只管"进入解释器的文本"，管不了已经在内存里的机器码。反射加载的 PE、注入的 shellcode，它一概看不见。
- 它是用户态机制，patch 只需要进程内的代码执行权限，门槛很低——这是它被反复针对的根本原因。
- 防守侧的补强：把 AMSI 结果接入行为链（脚本 → 子进程 → 网络外联）、同时开脚本块日志、用 ETW-TI 监控跨进程内存写入（第 11 章）、对 amsi.dll 做完整性监控。

## 七、和上一章的衔接

扫描器解决"磁盘上的坏文件"，AMSI 解决"解释器里的坏脚本"。两者有一个共同前提：<mark>内容必须在某个时刻以明文经过某个检查点</mark>。

攻击者要做的只有两件事：让内容绕过检查点，或者在到达检查点之前就变成机器码。前者是字符串混淆和编码，后者是内存加载和注入。下一章换一个层面——从系统启动的最早期开始，看安全软件是怎么抢在恶意驱动之前拿到执行权的。
