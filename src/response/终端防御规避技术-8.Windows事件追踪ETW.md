进程通知、对象回调、minifilter、WFP，谁想监听谁去注册。ETW 是另一套思路，系统自己就在广播大量事件，EDR 只是打开收音机去听。它的覆盖面比任何单一回调都宽，代价是广播可以被关掉、被改配置、被补丁打断。

## 一、ETW 是什么

ETW 全称 Event Tracing for Windows，Windows 自带的事件追踪框架。内核和用户态组件把事件写进一条"会话"，消费者从会话里读出来。可以想成一套广播系统：提供者是播音员，会话是频道，消费者是收音机，控制器是调音台。播音员把一段一段录音丢进频道，收音机调到这个频道就能听到；没开收音机的时候，播音几乎不花什么成本。

事件的通用结构分成两部分：

- **系统头**：提供者 GUID、事件 ID、版本、级别（Level）、关键字（Keyword）、时间戳、进程 ID、线程 ID、活动 ID。
- **用户数据**：由提供者的清单（manifest）定义，字段名和类型都在清单里。不同提供者的事件长什么样，全靠清单描述。

传输方式有三种：

- **实时会话**：事件先进内存缓冲区，消费者一边写一边读。
- **ETL 文件会话**：写进 `.etl` 文件，事后用工具分析，`logman`、Performance Monitor、WPA 都吃这种文件。
- **自动记录器（AutoLogger）**：开机时按注册表里的配置自动启动会话，关机才停。系统安全日志、Defender 的遥测大量用这种方式。

**ETW 的优势**

- 覆盖广：进程、线程、文件、注册表、网络、内存、脚本、WMI，全都有现成的提供者。
- 不需要改别人的代码：不像 Hook 要往 `ntdll` 里插跳转，ETW 是系统原生机制，不存在 Unhook。
- 开销可控：没人订阅时提供者的写入几乎不产生开销，订阅之后按级别和关键字过滤。
- 内核直接发的事件，用户态补丁改不掉，这一点在规避那一节会细说。

## 二、几个容易混的名词

### GUID

GUID 是 128 位的唯一标识符，格式是 8-4-4-4-12 的十六进制，外面套花括号：

```text
{22FB2CD6-0E7B-422B-A0C7-2FAD1FD0E716}
```

在 ETW 里，每个提供者有一个 GUID，控制器启用提供者时用的就是这个 GUID，不是名字。名字只是给人看的，系统内部认 GUID。会话也有 GUID，会话名和 GUID 是两套标识。

### RPC

RPC 是远程过程调用。客户端按"接口 + 方法"调过去，服务端执行完把结果送回来，调用方看起来像在调本地函数。Windows 里到处是 RPC：服务控制管理器、事件日志服务、注册表远程操作、WMI 远程查询，底层都走它。端口 135 是端点映射器，负责告诉客户端某个服务的实际端口。

ETW 的控制器和事件日志服务之间、WMI 的远程调用，底层都靠 RPC。攻击者做横向时盯 135 端口，就是因为这里能捅到一串服务。

### WMI

WMI 全称 Windows Management Instrumentation，Windows 的管理接口。它能查机器状态、枚举进程、读硬件信息、订阅事件，还能远程执行。底层的对象模型来自 CIM/WBEM，接口通过 COM/DCOM 调用，跨机器时走 RPC。

WMI 和 ETW 是两套并行的东西，不是替代关系。ETW 负责"发生了什么事件"，WMI 负责"管理和查询对象"。有意思的是 WMI 自己的活动也会产生 ETW 事件，`Microsoft-Windows-WMI-Activity` 这个提供者记录的就是 WMI 的查询和订阅行为。

### MOF

MOF 全称 Managed Object Format，一种描述语言，用来定义 WMI 的类、属性、方法和事件。写完用 `mofcomp.exe` 编译，注册进 WMI 仓库（`C:\Windows\System32\wbem\Repository`）。

早期 ETW 提供者也用 MOF 描述事件结构，现在基本改成清单（manifest）加 `mc.exe` 编译。看到老资料里写"MOF 提供者"，说的就是这种旧式定义方式。

### 三者的关系

```text
提供者（发事件）
   |
   | 事件写入会话缓冲区
   v
会话（频道，实时或 ETL）
   ^
   | 控制器通过 RPC 调事件日志服务，启动会话、启用提供者
   |
消费者（EDR 服务、logman、性能监视器）

WMI（管理接口，另一套体系）
   | 类定义来自 MOF，远程调用走 RPC/DCOM
   v
WMI 自己的活动也会写成 ETW 事件
```

## 三、ETW 的三个主要组件

### 提供者 Provider

提供者负责产生事件。用户态提供者先调用 `EventRegister` 注册，拿到一个注册句柄，之后用 `EventWrite`、`EventWriteTransfer` 写事件，结束时 `EventUnregister`。

清单文件（`.man`）里声明了每个事件的 ID、版本、级别、关键字和字段类型，`mc.exe` 把清单编译成头文件和资源，`wevtutil im` 装进系统。Windows 自带的提供者，像 `Microsoft-Windows-Kernel-Process`，是内核直接写事件，不经过用户态。

级别从 Critical、Error、Warning、Information 到 Verbose；关键字是一组位掩码，用来把事件分成不同通道，比如"审计成功""审计失败"。控制器启用提供者时可以指定级别和关键字，低于门槛的事件不产生，这是控制开销的主要手段。

### 消费者 Consumer

消费者读事件。实时消费的流程是 `OpenTrace` 打开会话，`ProcessTrace` 阻塞等待事件，回调函数里处理每条记录，最后 `CloseTrace`。

```c
EVENT_TRACE_LOGFILEW log = {0};
log.LoggerName = L"MySession";
log.ProcessTraceMode = PROCESS_TRACE_MODE_REAL_TIME | PROCESS_TRACE_MODE_EVENT_RECORD;
log.EventRecordCallback = OnEvent;

TRACEHANDLE handle = OpenTraceW(&log);
ProcessTrace(&handle, 1, NULL, NULL);
```

事件记录本身是二进制，字段要按清单解析，用 TDH 接口：`TdhGetEventInformation` 拿到结构，`TdhGetProperty` 按名字取字段。这也是为什么消费者必须知道提供者的清单，否则只能拿到一串字节。

权限上有门槛：读某些会话要管理员或者"Performance Log Users"组成员；消费 `Microsoft-Windows-Threat-Intelligence` 这类高敏感提供者，还需要 PPL-AM 身份。

### 控制器 Controller

控制器管会话：启动、配置、启用或禁用提供者、停止。

```c
StartTraceW(&session, L"MySession", &props);
EnableTraceEx2(session, &providerGuid, EVENT_CONTROL_CODE_ENABLE_PROVIDER,
               TRACE_LEVEL_INFORMATION, 0, 0, 0, NULL);
```

常用接口是 `StartTraceW`、`EnableTraceEx2`、`ControlTraceW`、`QueryAllTracesW`。会话属性里有缓冲区大小、缓冲区数量、刷盘间隔、丢失事件的处理方式，配不好就会丢事件。

**自动记录器**

开机自启的会话写在注册表：

```text
HKLM\SYSTEM\CurrentControlSet\Control\WMI\Autologger\<会话名>
```

键里有 `Start`、`Guid`、`FileName`、`Enabled`，每个提供者还有子键控制级别和关键字。安全产品和系统组件常用它保证重启之后立刻有日志。这个位置也是攻击者做配置篡改时的首选，后面会讲。

## 五、六类事件从哪来

| 事件类别 | 主要提供者 | 备注 | 盲区 |
|---|---|---|---|
| 进程创建 | Kernel-Process、Security-Auditing 4688、Sysmon 1 | ETW 直接给映像路径、命令行、父进程、会话 ID | 命令行审计默认不开，4688 可能没有参数 |
| 线程创建 | Kernel-Process | 给线程 ID、所属进程、起始信息 | 起始地址不一定能直接拿到 |
| 镜像加载 | Threat-Intelligence（ImageLoad）、Sysmon 7 | 给映像基址、大小、签名状态 | TI 需要 PPL；普通提供者不覆盖 |
| 注册表 | Kernel-Registry、Sysmon 12/13/14 | 创建、设置、删除、改名 | 查询事件量极大，通常只订设置和删除 |
| 文件操作 | Kernel-File、Sysmon 11/23/26 | 创建、写入、删除、改名 | 缓存写入可能不产生逐次事件，量大 |
| 网络事件 | Kernel-Network、TCPIP、Sysmon 3/22 | 连接、收发字节、目标地址 | 加密后只有元数据 |

几类事件的信息密度差别很大。进程创建给的是完整快照，文件写入给的是海量碎片，注册表设置给的是精确的键值变化。EDR 通常在进程事件上做全量采集，在文件和注册表事件上做采样和过滤，靠关联把碎片拼回去。

## 六、EDR 为什么爱用 ETW

把 ETW 和其他传感器放一起看：

- 进程、线程、镜像、注册表、文件、网络，一套框架全覆盖，不用为每类事件写一个驱动。
- 事件由系统产生，攻击者改不了生成端，只能改订阅端或者补丁调用点。
- 内核直接发的事件不经过用户态，`EtwEventWrite` 补丁对它无效。
- 开销按级别和关键字控制，产品可以按场景调节。

代价也真实：字段有限，很多细节拿不到；高流量场景会丢事件；订阅依赖会话，会话能被停掉；高价值提供者（TI）有 PPL 门槛。

所以成熟的 EDR 不会只用 ETW。回调给的是"确定发生"的事件，ETW 给的是"覆盖面广"的事件，两者互相补。回调被摘掉，ETW 还能看见；ETW 会话被停，回调还在拦。

## 七、规避 ETW 检测

### 补丁 EtwEventWrite

最常见的手法，把 `ntdll!EtwEventWrite` 的开头改成"返回 0"：

```c
// 原始开头一般是 4C 8B DC ...（x64）
// 改成：
BYTE patch[] = { 0x33, 0xC0, 0xC3 };  // xor eax, eax; ret
```

改完以后，这个进程里所有用户态提供者的写入都变成空操作，事件不再产生。同类目标还有 `EtwEventWriteFull`、`EtwEventRegister`、`NtTraceEvent`。有的工具连注册都不让成功，直接让 `EventRegister` 返回错误。

**这条手法的边界**

它只影响当前进程，也只影响用户态提供者。`Kernel-Process`、`Kernel-File`、`Kernel-Registry`、`Kernel-Network` 和 ETW-TI 的事件是内核直接写的，补丁打不到。所以补丁 `EtwEventWrite` 能藏住的是 PowerShell 脚本日志、.NET 运行库事件、厂商自己的用户态遥测，藏不住进程创建和文件落地。

### 修改提供者配置

- 把 Autologger 键下的 `Start` 改成 0，或者删掉 `Enabled`，重启后会话不再自启。
- 改提供者子键的级别，把 Information 降到 Error，关键事件直接不产生。
- 改 `FileName` 指向别的路径，日志写到看不见的地方。

### 篡改追踪会话

- `logman stop <会话名>`，或者用 `ControlTrace` 停止会话，需要管理员权限。
- 抢占同名会话，让真正的消费者拿不到数据。
- 删除、替换、截断 ETL 文件，让事后分析缺段。

### 干扰消费者

杀掉 EDR 的用户态服务，断掉 ETL 上传通道，回归上一章讲的卸载对抗。驱动还在，事件还在产生，只是没人收、没人报。

### 伪造事件

拿到合法提供者的注册句柄后自己写事件，往检测系统里灌噪声。这种做法成本高，效果也不稳定，但在关联分析里能起到混淆作用。

### 防守方怎么发现

- **内存比对**：把磁盘上的 `ntdll.dll` 和进程内存里的做哈希对比，函数头被改就会露出来。
- **函数字节扫描**：直接检查 `EtwEventWrite` 开头是不是 `33 C0 C3`，或者跳转到了非模块区域。
- **注册表基线**：监控 Autologger 键的写入，`Start`、`Enabled`、`FileName` 变化都算异常。
- **会话清单**：定期 `logman query -ets`，比对会话数量、提供者列表、级别设置。
- **事件缺失**：按进程或主机统计事件量，某个进程突然不再产生任何 ETW 事件，比产生异常事件更可疑。

ETW 这一类传感器有个特点：它不拦截，只记录。攻击者不需要绕过某条规则，只要让记录停下来就够了。所以检测的重点也从"事件内容"转到"事件有没有断"。

## 八、四套传感器总览

| 体系 | 覆盖 | 注册门槛 | 能否阻断 | 主要盲区 |
|---|---|---|---|---|
| 内核回调（Ob/Ps/Cm） | 句柄、进程线程、镜像、注册表 | OB 与 Ps 的 Ex 版本需要 AM 特权 | 能 | 字段有限、回调可被摘 |
| 微筛选器 | 文件与命名管道 | 普通签名驱动 | 能 | 直接卷访问、内存映射、可被卸载 |
| WFP | 网络连接与数据包 | 普通签名驱动 | 能 | 加密内容、回环流量 |
| ETW | 几乎全部系统事件 | 消费端部分需要 PPL | 不能 | 会话可停、用户态提供者可被补丁 |

四套体系叠在一起，才构成完整的可见性。单独看任何一套，都能找到"这一层看不见"的规避路径；叠起来之后，攻击者要同时让四层都失灵，成本和暴露风险都会高很多。

## 九、重点速记

- ETW 是系统自带的事件广播框架，提供者发、会话传、消费者收、控制器管。
- 提供者和会话都用 GUID 标识，名字只是给人看的。
- 事件结构分系统头和用户数据，用户数据靠清单或 TDH 解析。
- AutoLogger 在注册表 `HKLM\SYSTEM\CurrentControlSet\Control\WMI\Autologger` 下配置，开机自动启动。
- 进程和线程事件来自 `Kernel-Process`，文件来自 `Kernel-File`，注册表来自 `Kernel-Registry`，网络来自 `Kernel-Network`。
- 镜像加载和高价值内存事件要走 `Threat-Intelligence`，消费端需要 PPL-AM。
- 补丁 `EtwEventWrite` 只对当前进程的用户态提供者有效，内核事件照旧产生。
- 规避 ETW 的三种层次：补丁调用点、改提供者配置、停会话或干扰消费者。
- 检测 ETW 规避靠内存比对、函数字节扫描、注册表基线和事件缺失分析。
- WMI 是管理接口，MOF 描述它的类，RPC 是它们共同的底层调用通道。
