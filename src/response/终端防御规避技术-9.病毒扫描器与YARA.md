进程通知、对象回调、minifilter、WFP、ETW，全是被动接收。扫描器是另一套思路——它不等事件，而是主动去翻文件里到底写了什么。EDR 里负责"这个文件到底坏不坏"的那一环，通常就是扫描引擎加规则库。理解了扫描的触发方式和规则怎么写，才能看清签名检测的边界在哪。

## 一、扫描器简史

病毒扫描器不是一开始就长现在这样，它的形态是被病毒逼出来的。

- **1980 年代末**：主流是引导区病毒，感染软盘的引导扇区。扫描器做的最简单的事，就是把已知病毒的一段固定字节拿去和文件比对。命中就报警，不命中就放过。
- **1990 年代**：多态病毒出现，每次感染都改自己的字节，固定字符串全部失效。扫描器开始引入通配符、正则，以及仿真（emulation）——把样本放进一个模拟的 CPU 和系统环境里跑几步，看它自己解密出什么。这是后来沙箱和动态分析的前身。
- **2000 年代**：加壳、变形、蠕虫大规模爆发。扫描器加入通用解包器（unpacker）和启发式（heuristics），不再只认已知字节，开始看"像不像"。
- **2010 年代至今**：云查杀（把哈希和特征发到云端比对）、机器学习分类器、行为监控、内存扫描、信誉评分。

一句话概括这条演进：<mark>扫描器从"认识坏文件的字节"进化到"认识坏文件的动作"</mark>。但只要还依赖已知特征，它就永远落后于最新样本——这是签名检测的结构性短板，不是实现问题。

一个文件被扫描器处理，大致走这条链：

```text
文件落地
   |  引擎读取
   v
解包 / 解码（处理加壳、压缩、编码）
   |
   |  特征提取（哈希、字节序列、字符串、PE 结构）
   v
与规则库匹配
   |
命中 -> 报警 / 隔离 / 上报云端
未命中 -> 放行，可能进入深度分析队列
```

这条链上任何一环都可以成为规避入口：让文件不落地、让解包失败、让特征变形、让规则匹配不上，或者让扫描根本没机会发生。

## 二、两种扫描模式

| 维度 | 按需扫描（On-Demand） | 按访问扫描（On-Access） |
|---|---|---|
| 触发时机 | 用户手动、计划任务、全盘/指定目录 | 文件被打开、写入、执行、重命名、删除时 |
| 覆盖面 | 扫描范围内的全部文件 | 只覆盖实际发生交互的对象 |
| 性能开销 | 集中爆发，可以很重 | 分摊到每次 IO，必须很轻 |
| 分析深度 | 可解包、可仿真、可深度分析 | 通常只算哈希 + 少量快速特征 |
| 主要盲区 | 两次扫描之间的间隙 | 只在内存里存在、从不经过文件系统的载荷 |

### 按需扫描

按需扫描是最早的形态，也是最容易理解的形态：给定一个范围，遍历所有文件，逐个比对规则库。

它的优势是覆盖全、可以慢慢分析，适合做深度检查和事后取证。劣势同样明显：<mark>它只在"那一刻"有效</mark>。

### 假设攻击者

把攻击者想成一个知道扫描计划的人。他不需要破解扫描引擎，只需要利用扫描的时间模型：

1. 等第一次全盘扫描结束。
2. 把恶意文件放进系统。
3. 执行完毕，拿到需要的东西。
4. 在第二次扫描开始之前把文件删掉。

这样按需扫描从头到尾都没见过这个文件，而系统在两次扫描之间一直暴露在风险里。这不是理论上的漏洞，是"周期性检查"这个模型本身决定的间隙，通常叫扫描间隙（scan gap）。

所有基于"定期检查"的防护都有这个问题：EDR 的定期内存扫描、合规的月度漏洞扫描、日志的定期审计，逻辑都一样。差别只在于间隙有多长、间隙里还有没有别的传感器在盯。

### 按访问扫描

按访问扫描就是为了压缩这个间隙：不等定期检查，而是在对象被碰到的瞬间就检查。

它通常和一个"能在目标对象发生交互时收到通知"的组件配合使用——在 Windows 上这个组件就是**文件系统微筛选器**（minifilter，第 6 章讲过）。

minifilter 挂在文件系统的 IRP 路径上，能在这些操作的前置回调里拿到文件路径和操作类型：

- `IRP_MJ_CREATE`：文件被打开或创建。
- `IRP_MJ_WRITE`：内容被写入。
- `IRP_MJ_SET_INFORMATION`：重命名、删除。

拿到之后，筛选器可以**阻塞这次 IO**，把文件交给扫描引擎，等扫描结果回来再决定放行还是拒绝。这是同步拦截；也可以只做异步上报，不阻塞用户操作，代价是恶意文件可能已经被执行。

三种最典型的检查时机：

- **下载落盘**：浏览器、下载器、即时通讯工具写文件时，文件刚成形就被扫。
- **打开/执行**：`CreateProcess` 走到映像映射之前，扫描器有机会拦住。
- **删除**：清理型扫描，用于确认"删掉的东西是不是恶意"，也用于取证。

为了不让每次 IO 都重扫，引擎会维护一张"已扫描缓存"，键通常是文件 ID 加修改时间、大小、USN。文件一旦变动，缓存失效，下次访问重新扫描。这张缓存表本身也是攻防点：能改文件的元数据而不改内容，就可能让缓存误判为"没变"。

按访问扫描的能力边界很清楚：<mark>它只能看见经过文件系统的对象</mark>。反射式加载、进程注入、.NET 内存加载、无文件执行，全程不碰磁盘，minifilter 一个事件都收不到。这也是为什么后面还需要 AMSI 和 ETW-TI。

## 三、规则集

扫描器的核心不是引擎，是规则。引擎只是一个执行规则的机器：读文件、解包、把规则编译成匹配器、求值、返回结果。检测能力强不强，取决于规则库的覆盖面和质量。

常见的规则类型：

| 规则类型 | 例子 | 强度 | 弱点 |
|---|---|---|---|
| 文件哈希 | SHA-256 | 精确，几乎零误报 | 改一个字节就失效 |
| 区段哈希 | 只算 `.text` 的哈希 | 抗改元数据、抗加签 | 改代码即失效 |
| 字节序列 | `4D 5A 90 00 ...` | 灵活，可带通配 | 加花、重排即失效 |
| 字符串 | `"cmd.exe /c"` | 可读、易维护 | 编码、拆分可绕过 |
| 正则 | `/powershell.*-enc/` | 表达力强 | 性能差，误报高 |
| 逻辑组合 | 字符串 A 且 字符串 B 且 文件类型 | 降误报 | 维护成本高 |

### YARA

YARA 是目前广泛采用的开源规则标准，社区驱动，很多 EDR 厂商也直接用它做静态规则的一部分。它被青睐的原因不是"性能最好"，而是**格式灵活、表达能力强**：文本、十六进制、正则、布尔条件可以自由组合，既能写"精确到哈希"的窄规则，也能写"某个家族的通性"的宽规则。

厂商的私有规则库通常是 YARA 的超集（多了沙箱结果、信誉、云端情报），但结构和思路是同一套。

### 规则结构

一条 YARA 规则由几段固定元素组成：

```text
rule Suspicious_PowerShell_Encoded
{
    meta:
        description = "检测编码后的 PowerShell 命令"
        author      = "ezouy"
        reference   = "ATT&CK T1059.001"
        date        = "2024-05-01"

    strings:
        $ps  = "powershell" nocase
        $enc = "-enc" nocase wide ascii
        $b64 = /[A-Za-z0-9+\/]{40,}={0,2}/

    condition:
        uint16(0) == 0x5A4D or
        (all of ($ps*) and any of ($enc*) and $b64)
}
```

逐段看：

- **rule 行**：规则名，全局唯一，给人看也给引用用。
- **meta**：描述、作者、参考、日期、样本哈希。这些元数据**不参与匹配**，扫描器完全忽略它们，但它们是规则意图和来源的上下文——分析时判断"这条规则在防什么"全靠它。
- **strings**：要被搜索的内容，三种写法。
  - 文本：`"powershell"`，可加修饰符 `nocase`（忽略大小写）、`wide`（UTF-16）、`ascii`、`fullword`（整词匹配）、`xor`。
  - 十六进制：`{ 4D 5A 90 00 }`，支持通配 `??`、跳转 `[4-6]`、多选 `( 01 | 02 03 )`。
  - 正则：`/.../`，表达力最强，也最慢。
- **condition**：布尔表达式，决定"什么情况下算命中"。常用写法有 `any of them`、`all of ($a*)`、`2 of ($b*)`、`$a at 0`（指定偏移）、`filesize < 1MB`、`uint16(0) == 0x5A4D`（判断 MZ 头）、`pe.number_of_sections`、`for any i in (0..n)`。

### 变形与复杂规则

多态样本每次生成的字节都不一样，规则没法写"具体字节"，只能写"结构"。YARA 的十六进制语法就是为这个准备的：

- 通配跳过会变的字段：`{ 4D 5A ?? ?? 00 00 }`。
- 跳转允许中间插入花指令：`{ 8B 45 [2-8] 89 45 }`。
- 多选覆盖等价指令：`( E8 | E9 )` 对应 call 和 jmp 两种形态。
- 正则加锚点，只抓稳定片段。

代价是规则变宽，误报上升。所以宽规则通常在 condition 里再加文件类型、大小、区段特征做约束，把"像"收敛成"确实是"。

### 引擎怎么跑这些规则

规则在加载时被编译：所有 strings 编成一套多模式自动机（Aho-Corasick 一类），一次扫描可以同时匹配上千个模式，命中的候选再交给 condition 求值。规则库越大，编译和扫描越慢，所以实际产品会把规则分级——快速规则放在按访问扫描的同步路径上，重规则和仿真放到后台队列。

## 四、规避扫描器签名

按攻击链的位置分，规避手段可以归成几类。

**过哈希规则**

改一个不影响执行的字节，哈希就全变：

- 加一个空的 PE 节。
- 改 `TimeDateStamp`、`Checksum`。
- 重排资源节、改版本信息。
- 给文件追加不影响解析的填充数据。

行为完全不变，文件哈希和区段哈希都换了一套，靠哈希的规则全部失效。

**过字符串与字节规则**

- 字符串拆分、运行时拼接，比如 `"Am" + "si" + "ScanBuffer"`。
- 编码存储，运行时解码：Base64、XOR、AES、自定义编码表。
- 把字符串藏进资源节、数据节，运行时读出来再还原。
- 大小写变形、宽窄字符混用、Unicode 同形字替换。
- 指令替换：`mov eax, 1` 改成 `xor eax, eax; inc eax`。

**过深度分析**

- 加壳：UPX 及自定义壳，让静态特征看不到原始代码。扫描器要解包才看得见，壳做得越怪，解包失败的概率越高，失败就放行。
- 花指令：插入无意义跳转和废指令，打乱字节序列。
- 多态/变形引擎：每次生成不同形态，迫使规则只能写结构特征。

**利用扫描模型本身的缝**

- 落地、执行、删除，落在两次按需扫描之间。
- 只在内存执行：反射加载、进程注入、.NET 内存加载，磁盘上从不出现可扫文件。
- 分离加载器与载荷：磁盘上只有一个看起来无害的 loader。
- 借用系统自带的白名单程序（LOLBins）执行，文件本身不是恶意样本。

**破坏扫描器本身**

- 关服务、删规则库、改排除路径（需要管理员）。
- 用有漏洞的签名驱动摘掉 minifilter（BYOVD，第 6 章）。
- 改扫描缓存的元数据，让引擎以为文件没变。

对应的防守补强：

- 行为检测：扫描器看不到的，交给 ETW、内核回调、AMSI。
- 内存扫描：定期比对进程内存里的已知特征。
- 云信誉：第一次见到就上报，不等规则更新。
- 扫描缓存与 USN 日志：用来补"扫描间隙"期间的证据链。

## 五、这一章的位置

签名扫描解决的是"磁盘上的坏文件"，它的模型是"看过才知道"。规避的两条通用路径：<mark>让被看的东西变样，或者让它根本没机会被看</mark>。

后者正好是下一章要展开的问题——脚本没有文件，扫描器扫什么。
