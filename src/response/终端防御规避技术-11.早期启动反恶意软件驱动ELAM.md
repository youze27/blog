前面几章的传感器都有一个共同前提：系统已经起来，EDR 服务已经加载。但从内核初始化到安全软件驱动加载完成，中间有一段谁都没在看的空窗。bootkit 就是冲这段空窗来的。ELAM 是微软给反恶意软件厂商留的一条"比所有第三方驱动都早"的插槽，它解决的是启动顺序问题，不是检测能力问题。

## 一、驱动如何参与启动过程

一次完整的 Windows 启动大致是这条链：

```text
固件（UEFI/BIOS）
   |
   v
bootmgr
   |
   v
winload.exe  ── 加载 ntoskrnl.exe 和 boot-start 驱动
   |
   v
ntoskrnl.exe 初始化 ── 加载 system-start 驱动，初始化内核子系统
   |
   v
会话管理器（smss.exe）
   |
   v
服务控制管理器（services.exe）── 加载 automatic 驱动、启动服务
   |
   v
用户登录
```

驱动服务的 `Start` 值决定它在这个链条里的位置：

| Start | 类型 | 加载时机 |
|---|---|---|
| 0 | Boot | 由 boot loader 加载，最早的一批 |
| 1 | System | 内核初始化阶段，早于所有 automatic 驱动 |
| 2 | Automatic | 服务控制管理器启动时 |
| 3 | Manual | 按需加载 |
| 4 | Disabled | 不加载 |

同一批驱动内部，还要按"组"排序。组的顺序写在注册表里：

```text
HKLM\SYSTEM\CurrentControlSet\Control\ServiceGroupOrder
```

常见的组名和先后关系：

```text
Boot Bus Extender
System Bus Extender
SCSI miniport
Primary Disk
File System
PlugPlay
NDIS
```

每个服务项用 `Group` 指定自己属于哪一组。同一组内再按依赖关系和注册顺序排列。

这里有一个关键事实：<mark>Windows 允许第三方驱动以 boot-start 或 system-start 加载，而且它们和系统驱动混在同一批早期组里</mark>。加载顺序由配置决定，不由"是不是微软的驱动"决定。谁能把自己排到前面，谁就先执行。这个设计本身没有问题，但它给了恶意驱动一个明确的突破口。

## 二、bootkit 怎么利用这段顺序

bootkit 的目标不是"检测绕过"，而是"抢在其他驱动之前拿到内核执行权"。

典型做法：

1. 把恶意驱动注册成 `Start=0` 或 `1`。
2. 用 `Group` 把自己放进早期组，或者改依赖关系，让自己排到安全软件驱动之前。
3. 驱动在内核里跑起来之后，做这些事：
   - 摘掉 SSDT 或内联钩子（如果安全软件用了这些）。
   - 篡改内核回调链表：`PsSetCreateProcessNotifyRoutineEx` 注册的链表、`ObRegisterCallbacks` 注册的回调。
   - 修改调试相关标志，为后续 patch 内核铺路。
   - 直接阻止安全软件驱动加载：改它的服务项、改它的文件、或者在驱动加载路径上拦截。
   - 在文件过滤和注册表回调挂上之前，先把自己隐藏掉。

结果是安全软件的驱动要么根本没起来，要么起来了但看到的是被篡改过的内核结构，检测形同虚设。

历史上走这条路的家族不少，TDL-4/Alureon、Necurs 早期变种、部分 Rustock 变种都有 bootkit 阶段。它们的共同点是"抢顺序"，不是"正面硬碰检测"。

## 三、ELAM 驱动

微软的应对思路不是加强检测，而是把"谁先加载"这件事收归自己控制。

### 它是什么

ELAM 全称 Early Launch Anti-Malware，一种特殊签名的 boot-start 驱动。有三个硬性条件：

- 必须由微软用专门的 ELAM 证书签名，不是普通的 EV 或 WHQL 签名。证书链能追到微软，签发对象是经过审核的反恶意软件厂商。
- 只有通过 MVI（Microsoft Virus Initiative）审核的厂商才拿得到这张证书。
- 加载位置在所有第三方 boot-start 和 system-start 驱动之前，由内核的 ELAM 基础设施负责加载。

### 主要功能：在另一个驱动加载时接收通知并决定

ELAM 驱动的核心动作只有一件：注册一个启动驱动回调。

```c
NTSTATUS status = IoRegisterBootDriverCallback(BootDriverCallback, NULL);
```

之后内核每初始化一个 boot-start 驱动，就调用这个回调，把驱动信息交过来：

- 驱动文件路径。
- 签名状态和签名者。
- 文件哈希。
- 加载结果。

ELAM 根据这些信息返回一个分类：

| 分类 | 含义 | 策略影响 |
|---|---|---|
| BootDriverInitializedUnknown | 无法判定 | 取决于策略 |
| BootDriverInitializedGood | 判定可信 | 允许初始化 |
| BootDriverInitializedBadButNecessary | 恶意但属于必要驱动（如磁盘控制器） | 视策略放行 |
| BootDriverInitializedBad | 判定为恶意 | 拒绝初始化 |

策略本身也在注册表里：

```text
HKLM\SYSTEM\CurrentControlSet\Control\EarlyLaunch\DriverLoadPolicy
```

| 值 | 含义 |
|---|---|
| 0 | 只加载 Good |
| 1 | 加载 Good 和 Unknown（默认为此） |
| 3 | 再加 BadButNecessary |
| 8 | 全部加载（等于取消 ELAM 的拦截效果） |

### 判定逻辑

ELAM 自己不做深度分析，它依赖三样东西：

- **签名验证**：驱动有没有有效签名、签名者是不是已知的恶意软件厂商。
- **哈希比对**：文件哈希在不在已知恶意驱动库里。
- **厂商自己的判断**：ELAM 驱动里可以带一小段自有逻辑，把路径、名字、哈希送到自家引擎或本地库做判断。

所以 ELAM 的能力边界很清楚：<mark>它只在启动阶段、只对 boot-start 驱动、只做"加载或不加载"的判断</mark>。它不做运行时行为监控，也管不到 automatic 和 manual 启动的驱动。

### 验证过程是 Windows 安全功能的一部分

ELAM 的签名验证不是在 ELAM 驱动里做的，而是 Windows 自己的代码完整性机制的一部分：启动时内核会验证内核模块和驱动的数字签名，ELAM 只是被授予了一个"可以参与早期判定"的位置。

参与这个过程的门槛很高：

- 厂商要通过微软的反恶意软件审核（MVI）。
- 提交的 ELAM 驱动要经过微软签名，证书用途限定在 ELAM。
- 签名文件被吊销或过期，ELAM 就加载不了。

所以这不是一个"谁都能申请"的接口，而是微软和安全厂商之间的一条特许通道。

### ELAM 与 PPL-AM 的资格链

拿到 ELAM 签名不只是为了拦驱动。这条链继续往下延伸：

```text
MVI 审核 + 微软 ELAM 签名
        |
        v
获得反恶意软件（AM）特权
        |
        +--> 可以注册 ObRegisterCallbacks、PsSetCreateProcessNotifyRoutineEx 等
        |    高危回调（普通 WHQL 驱动注册不了）
        |
        +--> 可以创建 PPL-AM 级别的受保护进程
                |
                v
             可以消费 Microsoft-Windows-Threat-Intelligence 的 ETW 事件
```

这是一条从"启动顺序"一路延伸到"运行时最高可见度"的资格链。国内拿到完整链路的主要是火绒、瑞星、安恒、360 等几家（见中期总结），其余厂商多数走 minifilter、Cm 回调、ETW 这些不要求 AM 特权的路线。

## 四、规避 ELAM 驱动

ELAM 的覆盖窗口很短：系统启动完成、最后一个 boot-start 驱动初始化结束，它就退场了。所以规避思路不是"打败它"，而是"绕开它的时间窗"。

按成本从低到高：

1. **不用 boot-start**。把驱动设成 `Start=2`（automatic）或 `3`（manual），等 ELAM 结束之后再加载。这是最省事也最常用的方式，绝大多数恶意驱动根本不需要抢启动。
2. **改策略**。有管理员权限时把 `DriverLoadPolicy` 改成 8，ELAM 的 Bad 判定就失效。需要重启，而且这类注册表修改容易被完整性监控记录。
3. **停用 ELAM 服务**。把 ELAM 驱动的服务项改成 `Start=4`，或者删掉服务。同样需要管理员权限加一次重启，而且 PPL 保护可能直接阻止修改。
4. **打 ELAM 驱动本身**。它也是驱动，也在内存里。但它有签名保护，改内存需要内核写权限，还会撞上 PatchGuard 和代码完整性检查。
5. **换目标**。启动阶段进不去，就在运行阶段打安全软件的驱动：BYOVD（自带易受攻击的驱动）、摘 minifilter、摘回调（第 5、6 章）。

现实中的比例：bootkit 是少数，BYOVD 和运行时对抗是多数。ELAM 把 bootkit 的门槛抬高了，但没有改变"安全软件和攻击代码跑在同一个内核里"这个根本问题。

## 五、资格链的终点

ELAM 拿到的 AM 特权继续往下传：

```text
ELAM 签名
   |
   v
AM 特权
   |
   +--> 注册高危内核回调（OB、Ps 系列）
   +--> 创建 PPL-AM 受保护进程
           |
           v
        消费 Microsoft-Windows-Threat-Intelligence（ETW-TI）
```

ETW-TI 是这条链的最后一环，也是内核层可见度最高的一路数据。它的机制、和其他日志的区别、规避思路，单独放在[第 12 章](./终端防御规避技术-12.微软威胁情报ETW.md)讲。
