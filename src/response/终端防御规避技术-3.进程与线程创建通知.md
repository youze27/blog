EDR 在内核里订阅了两类事件：进程创建和线程创建。事件一发生，它就能拿到程序的路径、命令行，以及是谁启动的。攻击者要做的，要么是让这些字段变成假的，要么是让事件根本不发生。这一章讲的是第一类传感器，第四章讲的是另一类：谁打开了谁、拿到了什么权限。

## 1. 通知发生在哪一层

```text
用户态
  CreateProcessW  /  NtCreateThreadEx
        |
        | syscall
        v
内核
  建立 EPROCESS / ETHREAD，映射映像
        |
        | 遍历全局回调链
        v
  进程创建通知 / 线程创建通知
        |
        v
  主线程执行第一条指令
```

回调的窗口在"对象已经存在、代码还没开始运行"之间。EDR 在这个窗口里能读到映像路径、命令行、父进程，也能直接拒绝创建；攻击者拿到进程句柄后，同样能在这个窗口里改内存、改入口、排队 APC。

回调的工作方式更像小区门口的报警器：物业（内核）装上它之后，只要有人搬进来（创建进程），它就把"谁搬来的、住哪一户、从哪个门进"报给保安（EDR）。报警器不拦人，只报信；拦不拦、怎么拦，是保安后面的事。

**回调不是 Hook**
<ins>Hook 是在别人家门口挖个坑，改的是代码路径；回调是在门口装个门铃</ins>，只订阅事件。回调不碰 `ntdll` 的字节，所以 Unhook、直接系统调用、重新映射 `ntdll` 都绕不过它；但回调只能拿到内核传进来的字段，看不到用户态接下来要执行什么。

## 2. 注册与运行规则

### 2.1 注册接口

```c
// 进程创建/退出通知
PsSetCreateProcessNotifyRoutineEx(OnProcessNotify, FALSE);  // 注册
PsSetCreateProcessNotifyRoutineEx(OnProcessNotify, TRUE);   // 注销

// 线程创建/退出通知
PsSetCreateThreadNotifyRoutineEx(OnThreadNotify);           // 注册
PsRemoveCreateThreadNotifyRoutine(OnThreadNotify);          // 注销
```

- `PsSetCreateProcessNotifyRoutine` 是旧接口，只有 `ParentId`、`ProcessId`、`Create` 三个参数。
- `PsSetCreateProcessNotifyRoutineEx` 多了 `PS_CREATE_NOTIFY_INFO`，能拿到映像路径、命令行、创建者线程，还能拒绝创建。
- `Create` 为 `TRUE` 表示创建，`FALSE` 表示退出；退出通知常被用来计算进程存活时间。
- 注销要在驱动卸载之前完成，回调还挂在链上时卸载驱动会直接蓝屏。

### 2.2 回调的运行环境

回调运行在 `PASSIVE_LEVEL`，多数情况下处在发起创建的那个线程上下文里。它不能阻塞，不能等 I/O，不能调用可能重入的 API。EDR 一般只做两件事：把字段拷贝到自己的队列，剩下的交给工作线程处理。

**为什么回调里不能做重活**
回调卡住，整个进程创建流程就卡住，系统会明显变慢甚至无响应；回调里如果再去打开文件、读注册表，可能触发另一个回调，形成递归。所以成熟的 EDR 在回调里只记录"谁、什么时候、创建了什么"，签名校验、哈希计算、规则匹配都放到用户态异步做。

### 2.3 注册门槛

`PsSetCreateProcessNotifyRoutineEx` 要求驱动映像带 `/INTEGRITYCHECK` 链接选项，并且回调函数地址必须落在驱动自己的映像里，不能指向运行时分配的内存。这条限制把"随便写个驱动就能监控进程"的路堵了一半，也是 EDR 厂商驱动必须签名备案的原因之一。

**多个安全产品同时注册会怎样**
回调链是全局的，装了两套 EDR 就有两份回调，一个创建事件会被看两遍。回调之间互不感知，谁先注册谁先跑；某一份回调拒绝创建，后面的回调仍然会被调用。这也是"装两个杀软更容易蓝屏/卡顿"的技术原因。

## 3. 进程创建通知能拿到什么

`PS_CREATE_NOTIFY_INFO` 带着创建时的关键信息，各字段的可信度并不一样：

| 字段 | 含义 | 攻击者能否影响 |
|---|---|---|
| `ParentProcessId` | EPROCESS 里的父进程 ID | 能，通过 `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS` |
| `CreatingThreadId` | 真正调用创建 API 的线程 | 不能直接改 |
| `ImageFileName` | EPROCESS 内 15 字符的短名 | 需要内核写权限 |
| `CommandLine` | 创建时的命令行快照 | 创建后可改 PEB |
| `FileObject` | 映像文件对象，可取完整路径、签名、哈希 | 不易 |
| `CreationStatus` | 回调可写，写入错误码即可拒绝创建 | — |

**短名只有 15 个字符**
`EPROCESS.ImageFileName` 只有一个 15 字节的字符数组，放不下完整路径。所以 EDR 显示 `svchost.exe` 而不是 `C:\Windows\System32\svchost.exe` 时，不一定是它偷懒，而是这个字段就这么长。要拿完整路径，得用 `FileObject` 反查，或者从进程的 `SectionObject` 取。

**命令行只是创建时的快照**
`CommandLine` 指向的 `UNICODE_STRING` 只在回调期间有效，回调返回后可能被释放，EDR 必须在回调里拷贝走。它记录的是创建那一刻的内容；进程跑起来之后，PEB 里的命令行可以被改写，档案里留的还是原话。

**能拒绝，但只有 Ex 版本**
在 `PS_CREATE_NOTIFY_INFO.CreationStatus` 里写 `STATUS_ACCESS_DENIED`，创建直接失败，调用方收到错误，等于当场把人拦在门外。旧接口做不到这一点，只能等进程跑起来再杀。这也是现代 EDR 能在勒索软件落地第一个文件之前就把它拦掉的原因。

### 3.1 旧接口的竞态

`PsSetCreateProcessNotifyRoutine` 只给 PID。驱动拿到 PID 后要调用 `PsLookupProcessByProcessId` 查 `EPROCESS`，这中间有时间差：

- 进程可能已经退出，查不到，`PsLookupProcessByProcessId` 返回 `STATUS_NOT_FOUND`。
- PID 可能已经被复用，查到的是另一个进程，读取的路径、命令行全是错的。

这类"先拿 ID 再查对象"的写法天然存在 TOCTOU 问题。这很像先记下身份证号再去档案室查人：人可能已经走了，号也可能已经被别人用了。Ex 接口把对象指针直接递过来，就是为了消掉这段窗口。

## 4. 线程创建通知

### 4.1 字段与时机

旧接口只给 `ProcessId`、`ThreadId`、`Create`。Ex 接口给 `PEPROCESS` 和 `PETHREAD` 指针，可以直接读线程的起始地址、所属进程、创建时间。

**通知不是在线程对象建好时发**
线程创建通知在线程真正开始执行时才发出。用 `CREATE_SUSPENDED` 创建的线程，在 `ResumeThread` 之前不会产生通知。

挂起期间线程还没开始执行，攻击者正好利用这段时间改线程上下文、写内存、排队 APC，EDR 看不到。

这个时间差是 Early Bird、线程劫持、挂起进程注入的共同基础。它不是说回调没用，而是说"创建"和"执行"之间还有一段可以动手的缝。

### 4.2 起始地址是主要判据

**远程线程注入是什么**
A 进程先用 `OpenProcess` 打开 B 进程，再用 `CreateRemoteThread` 在 B 里开一条新线程，让这条线程去执行写进 B 内存的代码。好比外人穿上你公司的工服，在你的办公室里开了一条新的流水线——线程是 B 的，活是 A 派的。线程创建通知就是抓这个动作的传感器。

线程的起始地址可以用 `NtQueryInformationThread(ThreadQuerySetWin32StartAddress)` 查。正常线程的起始地址落在某个已加载模块的代码段里；远程线程的起始地址经常落在私有可执行内存，或者根本不属于任何模块。

但这条判据不绝对：

- `CreateRemoteThread` 的起始地址可以指向 `LoadLibraryW`，看起来完全合法。
- Early Bird 和 APC 注入的线程起始地址仍是 `ntdll!BaseThreadInitThunk` 或 `kernel32!BaseThreadInitThunk`，单看地址会漏。
- 线程劫持不创建新线程，连通知都没有。

所以线程通知要和内存扫描、调用栈、APC 队列一起看，单靠一个字段不够。

### 4.3 线程通知的盲区

| 行为 | 是否产生线程通知 | 原因 |
|---|---|---|
| `CreateRemoteThread` | 是 | 新线程，恢复时通知 |
| 挂起线程后不恢复 | 否 | 通知要等线程开始执行 |
| `QueueUserAPC` 到已有线程 | 否 | 复用现有线程 |
| 线程劫持（改上下文） | 否 | 不创建线程 |
| 空心化后恢复主线程 | 是（主线程） | 恢复时通知 |

## 5. 从事件到判定

单个事件信息有限，EDR 真正做判断靠的是把事件串起来：

```text
WINWORD.EXE (PID 4100)
  └─ cmd.exe (PID 5120)         cmd /c powershell -nop -w hidden -enc ...
       └─ powershell.exe (PID 5124)
            └─ rundll32.exe (PID 5130)     C:\Users\Public\a.dll
```

| 信号 | 正常样子 | 异常样子 |
|---|---|---|
| 父子关系 | explorer 拉起浏览器、Office 拉起自身组件 | 文档进程拉起命令行、命令行拉起脚本宿主 |
| 命令行 | 参数短、路径明确 | `-enc`、`-w hidden`、`IEX`、`DownloadString`、`mshta http` |
| 映像路径 | `Program Files`、`System32` | `%TEMP%`、`%APPDATA%`、`C:\Users\Public` |
| 签名 | 有效且发行者可信 | 无签名、签名吊销、发行者陌生 |
| 存活时间 | 长期驻留 | 秒级退出（loader） |

**关联规避**
第一章提过风险分累积：执行未签名程序、非典型子进程、分配可读写执行内存，各自加分，窗口内累计超过阈值就告警。攻击者的目标不是"每一步都干净"，而是"每一步的分都不够高"。所以常见手法是把动作拆开：先用合法进程加载，再等一段时间，再外联。

**误报从哪来**
安装包、运维脚本、浏览器更新器都会出现"文档进程拉起命令行""临时目录执行""无签名小程序"。EDR 必须靠白名单、基线、签名链和上下文把这类行为摘出去，否则告警会被淹没。

## 6. 规避技术

### 6.1 PPID 伪造

PPID 伪造就是把新进程的"父亲"栏改成另一个进程，让它看起来是某个可信系统进程亲生的，而不是由命令行拉起来的。

`CreateProcess` 支持 `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS` 属性，可以指定新进程"记在谁名下"：

```c
STARTUPINFOEXW si = {0};
si.StartupInfo.cb = sizeof(si);

SIZE_T size = 0;
InitializeProcThreadAttributeList(NULL, 1, 0, &size);
si.lpAttributeList = (LPPROC_THREAD_ATTRIBUTE_LIST)HeapAlloc(GetProcessHeap(), 0, size);
InitializeProcThreadAttributeList(si.lpAttributeList, 1, 0, &size);

HANDLE hParent = OpenProcess(PROCESS_CREATE_PROCESS, FALSE, parentPid);
UpdateProcThreadAttribute(si.lpAttributeList, 0, PROC_THREAD_ATTRIBUTE_PARENT_PROCESS,
                          &hParent, sizeof(hParent), NULL, NULL);

CreateProcessW(NULL, L"C:\\Windows\\System32\\notepad.exe", NULL, NULL, FALSE,
               EXTENDED_STARTUPINFO_PRESENT | CREATE_SUSPENDED,
               NULL, NULL, &si.StartupInfo, &pi);
```

**它改的是记录，不是事实**
新进程的 `InheritedFromUniqueProcessId` 被写成指定父进程的 PID，同时会继承这个父进程的令牌、可继承句柄、优先级等属性。所以伪造父进程不只是为了让进程树好看，还能顺带拿到更高权限——把一个普通进程"挂"到 `winlogon.exe` 名下，令牌也跟着变成 SYSTEM 级别。前提是能打开目标父进程，且拥有 `PROCESS_CREATE_PROCESS` 权限，通常要 `SeDebugPrivilege`。

**检测点**
`CreatingThreadId` 记录的是真正调用创建 API 的线程。如果 `ParentProcessId` 指向的进程里根本找不到这个线程，父子关系就是假的。再叠加时间关系（父进程比子进程还晚创建）、路径关系（`svchost.exe` 的子进程落在临时目录），误报率很低。

### 6.2 命令行篡改

做法是先报一句无害的话占位，等 EDR 记完，再改掉进程自己手里的口供。

流程是先以正常命令行创建进程，再改它 PEB 里的命令行：

```text
CreateProcess(notepad.exe, 用长参数占位, CREATE_SUSPENDED)
NtQueryInformationProcess(ProcessBasicInformation) -> PebBaseAddress
ReadProcessMemory(PEB.ProcessParameters) -> CommandLine (Buffer/Length/MaximumLength)
WriteProcessMemory(CommandLine.Buffer, 新内容)
WriteProcessMemory(CommandLine.Length, 新长度)
ResumeThread
```

**限制**
新内容不能超过 `MaximumLength`，所以只能改短或等长。常见做法是创建时塞一段很长的无害参数当占位，再把前面覆盖成真正的恶意命令。缓冲区在进程私有内存里，跨进程写需要 `PROCESS_VM_WRITE`。

**它骗的是事后查询**
进程创建回调记录的是创建那一刻的命令行，改 PEB 改不掉这份快照。这条技术针对的是那些靠 WMI、`Get-CimInstance`、定时轮询 PEB 拿命令行的 EDR。检测方法也直接：创建快照和运行时读取的内容对不上，就说明有人动过 PEB。

### 6.3 四大进程镜像修改技术

这四种技术解决同一个问题：让"磁盘上的文件"和"内存里真正跑的代码"不是同一个东西。Hollowing 改造的是已经存在的进程；Doppelgänging、Herpaderping、Ghosting 属于"基于 Section 的进程创建"，利用文件、映射、删除之间的时间差。

#### 6.3.1 进程空心化 Process Hollowing

先启动一个合法程序并把它暂停，再把进程内存里原来的代码全部掏空，填入恶意代码后恢复运行。整个过程像是在一间挂着合法公司招牌的办公室里换掉所有家具：任务管理器看到的是 `notepad.exe`，实际跑的是木马。

```text
CreateProcess(合法程序, CREATE_SUSPENDED)   回调看到合法映像，签名正常
  -> NtUnmapViewOfSection 卸载原映像（掏空）
  -> VirtualAllocEx 分配内存
  -> WriteProcessMemory 写入恶意 PE
  -> SetThreadContext 改入口点
  -> ResumeThread
```

EDR 在创建时看到的是一个签过名的 `svchost.exe`，路径、签名、父进程都正常；异常在内存里：PE 头、节区、入口点、映像基址，任何一项和磁盘文件对不上都可疑。

磁盘上的文件始终没变，被替换的只有内存里已经存在的进程镜像。

#### 6.3.2 进程替身 Process Doppelgänging

这种技术利用 NTFS 事务（TxF）：先在事务里写入恶意文件，把它映射成内存镜像，然后回滚事务。磁盘上不会留下病毒文件，但内存里的镜像还在，可以直接用它创建进程。等于是把病毒写在草稿本上，系统读进内存后一键撤销草稿，硬盘干干净净，内存里却已经留下了副本。

Doppelgänger 在德语里是"替身、二重身"的意思。国内有人把它音译成"多普勒"，其实和物理上的多普勒效应没有关系。

```text
NtCreateTransaction
  -> NtCreateFile（事务内）写入 payload
  -> NtCreateSection（事务内）映射镜像
  -> NtRollbackTransaction 回滚，磁盘文件消失
  -> NtCreateProcessEx（基于 Section）
  -> NtCreateThreadEx
```

依赖 TxF，而 TxF 在新版 Windows 上逐步废弃，很多场景已经不可用，所以这种技术的实际使用面在缩小。

检测点：进程映像路径为空或指向不存在的文件、Section 不是来自正常文件路径、事务相关 API 与回滚事件。

#### 6.3.3 进程赫帕德林 Process Herpaderping

先把恶意文件写到磁盘并映射成内存镜像，在真正启动线程之前，把磁盘上的原文件覆盖成干净内容，再启动进程。此时内存里是恶意代码，磁盘上却是一个无害文件。

```text
写入 payload 到磁盘，保持文件句柄不关闭
  -> NtCreateSection 映射镜像
  -> NtCreateProcessEx 创建进程对象
  -> 覆盖磁盘文件为干净内容
  -> NtCreateThreadEx 启动主线程
```

EDR 收到进程创建通知后去磁盘取样本、算哈希，看到的是干净文件，于是放行；它不知道内存里的 Section 早就是恶意内容。

检测点：进程创建期间文件被改写、Section 哈希与磁盘哈希不一致、文件句柄长时间不关闭、创建快照与磁盘内容存在时间差。

磁盘上的文件仍然存在，只是内容已经不是启动时的那一份。

#### 6.3.4 进程幽灵化 Process Ghosting

先建一个临时文件写入恶意程序，把它标记为待删除，映射成内存镜像后关闭句柄。文件会从磁盘上消失，再用这个已经没有实体的镜像启动进程。

```text
NtCreateFile（delete-on-close）写入 payload
  -> NtCreateSection 映射镜像
  -> NtClose 关闭句柄，文件被删除
  -> NtCreateProcessEx（基于 Section）
  -> NtCreateThreadEx
```

EDR 想查这个进程对应的原始 exe，磁盘上已经没有这个文件，查无此样本。和 Herpaderping 的区别是：Herpaderping 的文件还在，只是被换成干净内容；Ghosting 的文件直接没了。

检测点：映像路径对应的文件不存在、Section 来源异常、进程创建时文件已被删除。

**四种技术对比**

| 技术 | 核心套路 | 磁盘最终状态 | 本质 |
|---|---|---|---|
| Hollowing 空心化 | 创建挂起进程，掏空内存换代码 | 原文件不变 | 改已有进程的内存 |
| Doppelgänging 替身 | NTFS 事务里写文件，映射后回滚 | 事务回滚，不留文件 | 借事务抹掉磁盘痕迹 |
| Herpaderping 赫帕德林 | 映射后、启动前覆盖磁盘文件 | 文件还在，内容变干净 | 内存恶意，磁盘伪装 |
| Ghosting 幽灵化 | 标记删除，映射后删文件再启动 | 文件不存在 | 无磁盘实体的镜像 |

四种技术都在和进程创建回调抢时间：回调只负责报信，真正判断"文件是不是恶意"要靠后面去磁盘取样本、比对内存。攻击者卡的就是"回调已经响、样本还没取到"这段空档。

### 6.4 Fork&Run

loader 创建或注入一个合法进程，把 shellcode 放进去，然后 loader 自己退出，后续 C2 通信由合法进程完成。

回调看到的是 `rundll32.exe`、`dllhost.exe` 这类白名单进程被正常创建；异常信号在别处：loader 存活时间只有几秒、宿主进程被跨进程写入、宿主进程没有子进程却突然外联。

**为什么叫 Fork&Run**
"fork" 是派生一个新进程，"run" 是让它在里面跑。恶意代码不落地成独立程序，而是寄生在合法进程里，进程树和签名检查都会放行。

### 6.5 Early Bird

```text
CreateProcess(合法程序, CREATE_SUSPENDED)
VirtualAllocEx + WriteProcessMemory 写入 shellcode
QueueUserAPC(shellcode, 主线程)
ResumeThread
```

APC 在进程入口点之前执行，所以恶意代码比程序本身的初始化代码跑得还早。线程通知在 `ResumeThread` 时才发出，此时 APC 已经在队列里；回调只看到"有个线程要跑了"，看不到 APC 的内容。

**检测难点**
线程起始地址仍是 `BaseThreadInitThunk`，看起来完全正常。要发现它，得查挂起进程的私有可执行内存、APC 队列（普通回调拿不到 `KAPC` 结构），或者等 shellcode 跑起来后看行为。

### 6.6 线程劫持与 APC 注入

线程劫持的流程是：打开目标线程，`SuspendThread`，`GetThreadContext`，把 `Rip` 改成 shellcode 地址，`SetThreadContext`，`ResumeThread`，执行完再改回去。

整个过程不创建进程，也不创建线程，两类创建通知都看不到。检测只能靠 `Microsoft-Windows-Threat-Intelligence` 这类 ETW 事件（`SetThreadContext`、`SuspendThread`）、内核 Hook，或者栈回溯发现返回地址不在预期模块。

APC 注入到已有线程也是同样的道理：复用现有执行体，绕开"创建"这个观察点。

### 6.7 组合与盲区

成熟的手法不会只用一招，常见组合是：

- PPID 伪造让进程树看起来正常；
- 白加黑或签名程序做宿主，绕过签名检查；
- 空心化、赫帕德林或 Fork&Run 让磁盘上的文件和内存里的代码不一致；
- 线程劫持或 APC 注入避免产生新的线程事件；
- 全程控制节奏，把风险分压在阈值以下。

这套组合针对的正是创建通知的三个弱点：字段可伪造、事件可避开、执行内容看不到。

## 7. 技术对照

| 技术 | 进程创建通知 | 线程创建通知 | 主要检测点 |
|---|---|---|---|
| PPID 伪造 | 看到，但父进程字段是假的 | — | `CreatingThreadId`、时间关系 |
| 命令行篡改 | 看到真实快照 | — | 快照与运行时 PEB 不一致 |
| 空心化 Hollowing | 看到合法映像 | 看到主线程 | 内存与磁盘不一致、入口点 |
| 替身 Doppelgänging | 看到进程，映像路径可能为空 | 看到主线程 | Section 来源、事务回滚 |
| 赫帕德林 Herpaderping | 看到合法映像 | 看到主线程 | 磁盘文件在创建期间被改写 |
| 幽灵化 Ghosting | 看到进程，对应文件已删除 | 看到主线程 | 映像文件不存在 |
| Fork&Run | 看到合法宿主 | 看到宿主线程 | loader 短命、跨进程写、外联 |
| Early Bird | 看到合法进程 | 恢复时才看到 | 私有可执行内存、APC |
| 线程劫持 | 看不到新进程 | 看不到新线程 | 上下文修改、栈回溯 |
| APC 注入已有线程 | 看不到 | 看不到 | APC、栈、内存扫描 |

## 8. 重点速记

进程和线程创建通知是 EDR 在"出生登记处"的摄像头。它记录的是内核愿意给的字段，不是攻击者的全部动作；攻击者能改的是字段的来源，或者让事件根本不发生。

- 进程通知用 `PsSetCreateProcessNotifyRoutineEx`，能拿路径、命令行、创建者线程，也能直接拒绝创建。
- 线程通知在线程开始执行时才发，挂起线程不触发，这是 Early Bird 和挂起注入的时间窗。
- 字段可信度大致是：`CreatingThreadId`、`FileObject` 高于 `ImageFileName`，高于 `ParentProcessId`，高于运行时再读的 `CommandLine`。
- 四种镜像修改技术分别对应：换内存（Hollowing）、借事务（Doppelgänging）、改磁盘（Herpaderping）、删磁盘（Ghosting）。
- 三类绕过：伪造字段（PPID、命令行）、替换映像（四种镜像技术）、复用执行体（Fork&Run、线程劫持、APC）。
- 检测三件套：进程血缘、内存与磁盘一致性、创建快照与运行时对比。

创建通知回答的是"谁来了"，回答不了"它要干什么"。后半句要靠内存、线程和网络去补。
