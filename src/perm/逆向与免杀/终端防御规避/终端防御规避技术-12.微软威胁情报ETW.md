`Microsoft-Windows-Threat-Intelligence`（ETW-TI）。它不是给运维排错用的通用跟踪，而是微软专门为端点检测（MDE）打造的行为传感器。理解了它和普通日志的差别，才能明白为什么它是整条 ELAM → PPL-AM 资格链的终点。

## 一、MDE 是什么

在讲 ETW-TI 之前，得先弄清楚它的主人是谁。

MDE 全称 Microsoft Defender for Endpoint（旧称 ATP），微软自家的企业级 EDR 平台。它的结构和所有 EDR 一样：终端装一个传感器（Agent），把行为数据源源不断传到云端，蓝队在云端门户（`security.microsoft.com`）上看告警、拼攻击链、做狩猎和处置。

MDE 的本地传感器，就是这本书前面所有章节拆解的对象的集合：

- ELAM 驱动开机最早加载（第 11 章）。
- 内核里注册 OB 回调、minifilter、WFP（第 4、6、7 章）。
- EDR 主进程开 PPL-AM 自我保护。
- AMSI 拦截脚本载荷（第 10 章）。
- ETW-TI 持续采集全链路行为。
- 本地扫描器扫文件和内存（第 9 章）。

一个最容易混的点：**Windows Defender 杀毒和 MDE 不是一回事**。

- **Windows Defender（Defender Antivirus）**：个人版 Windows 默认自带的单机杀毒，管文件扫描和病毒查杀。
- **MDE（Defender for Endpoint）**：企业版 EDR 平台，要企业许可证才能完整启用。它把 ETW-TI、全套内核监控、云端分析整条链路打开。

个人电脑哪怕开着 Defender 杀毒，没有接入 MDE 租户，ETW-TI 这条采集链路就不会完整工作。MDE 之所以特殊，在于它直接复用微软原生内置的能力（ELAM、PPL、ETW-TI、AMSI 全是系统自带的），不需要像第三方 EDR 那样自己再开发一套独立驱动。这是它和其他 EDR 最大的架构差别。

## 二、ETW-TI 是什么

提供者名 `Microsoft-Windows-Threat-Intelligence`，GUID：

```text
{F4E1897C-BB5D-5668-F1D8-040F4D8DD344}
```

它在内核里发出的是高价值的"攻击行为"事件，而不是文件特征：

- 跨进程内存操作：`VirtualAllocEx`、`WriteVirtualMemory`、`ReadVirtualMemory`、`ProtectVirtualMemory`。
- 线程注入：`CreateRemoteThread`、`QueueUserAPC`、`SetThreadContext`。
- 映像加载：哪个进程把哪个映像映射进了哪个目标进程。
- 与凭据、令牌、进程创建相关的敏感操作。

每条事件都带发起者进程/线程、目标进程和调用栈。注入、无文件攻击、内存马都绕不开这几类操作，所以 ETW-TI 是目前内核层可见度最高的一路数据。

## 三、和其他 Windows 日志的区别

既然它也是"采集日志"，那和 Windows 上其他日志有什么不同？先把三类东西分开：

1. **Windows 事件日志（EventLog）**：`eventvwr.msc` 里看到的系统、安全、应用程序日志。
2. **普通 ETW**：各个子系统独立的提供者（进程、文件、网络各一个），零散。
3. **ETW-TI**：ETW 里的一个特殊定制提供者，但设计目标和普通 ETW 完全不同。

逐项对比：

| 维度 | EventLog（事件查看器） | 普通 ETW | ETW-TI |
|---|---|---|---|
| 定位 | 系统审计、运维排错 | 通用跟踪、性能调试 | MDE 专用威胁行为传感器 |
| 存储 | 落地成 evt 文件 | 可实时流，可选落盘 | 实时流优先，供给 MDE 云端 |
| 进程族谱 | 弱，父 PID 容易被篡改 | 一般，链路容易断 | 强，专门维护进程链 |
| 字段丰富度 | 少 | 中等，各 Provider 参差 | 丰富（调用栈、模块、上下文） |
| 性能开销 | 磁盘 IO 大，只记低频审计 | 可实时但需手动整合多个会话 | 低开销持续采集高频行为 |
| 默认状态 | 默认开启 | 大多默认不启动会话 | MDE 启用时自动激活 |
| 逃逸难度 | 可清日志、篡改事件 | 可停会话、过滤 | 与 MDE、PPL 绑定，难度更高 |

几个关键差距展开说。

**设计目标**。EventLog 是早期 Windows 为运维、排错、审计设计的，不是为攻击检测设计的。普通 ETW 偏性能和调试。ETW-TI 从第一天起就是为了对抗攻击者、做攻击链溯源。

**事件颗粒度和上下文**。这是最大的差距。EventLog 的进程创建日志（4688）默认很多环境没开，就算开了也容易丢父进程链、缺调用栈、缺模块信息。普通 ETW 颗粒度中等，但进程之间关联弱，很难自动拼出完整攻击链。ETW-TI 的进程创建事件自带父进程、祖先进程链、命令行、镜像路径、线程调用栈、加载模块、相关文件和网络上下文——可以直接拼出完整的攻击图谱（Process Graph），也就是 MDE 后台看到的那条攻击链。

**进程族谱能力**。EventLog 4688 的父 PID 很容易被篡改，父子关联容易断。ETW-TI 专门维护进程族谱，跨线程、跨子进程追踪，攻击者想简单改个 PID 就切断攻击链，难度高很多。

**采集模式**。EventLog 写磁盘，开销大，只适合低频审计。普通 ETW 可以实时流，但 Provider 零散，要开一堆会话再整合，配置麻烦。ETW-TI 是流模式实时上报，设计初衷就是低开销持续采集高频行为，一个提供者就覆盖进程、模块、文件、网络相关行为，直接喂给 MDE 云端。

一句话总结这个区别：<mark>EventLog 和普通 ETW 是普通监控摄像头，ETW-TI 是专门针对犯罪行为优化、自动识别人物关系、记录完整行动链路的智能摄像头，数据直接喂给 MDE 后台做告警</mark>。它只负责采集行为链路，本身不直接拦截程序运行——拦截是 OB 回调、minifilter、AMSI 那些层的事。

## 四、谁能消费

<mark>只有 PPL-AM 级别的进程能订阅这个提供者</mark>。普通管理员即使拿到 SYSTEM 令牌也读不到，`EnableTraceEx2` 打开这个提供者时，内核会校验调用者的保护级别。

这就是为什么 ELAM 签名是整条链的起点——没有 AM 特权，就没有 PPL-AM，也就没有 ETW-TI。消费代码和普通 ETW 一样，差别只在权限：

```c
StartTraceW(&session, L"TI", &props);
EnableTraceEx2(session, &tiGuid, EVENT_CONTROL_CODE_ENABLE_PROVIDER,
               TRACE_LEVEL_INFORMATION, 0, 0, 0, NULL);

EVENT_TRACE_LOGFILEW log = {0};
log.LoggerName = L"TI";
log.ProcessTraceMode = PROCESS_TRACE_MODE_REAL_TIME | PROCESS_TRACE_MODE_EVENT_RECORD;
log.EventRecordCallback = OnEvent;
TRACEHANDLE handle = OpenTraceW(&log);
ProcessTrace(&handle, 1, NULL, NULL);
```

## 五、确定事件的来源

ETW-TI 事件里最有用的两个字段：

- **调用栈（CallStack）**：一组返回地址，能指出这次内存写入是从哪个模块、哪个函数发起的。
- **发起者进程/线程 ID**：能定位"谁在操作谁"。

把这两样和第 3、5 章的进程创建、镜像加载事件拼起来，就能还原完整的注入链：哪个进程创建了哪个线程、往哪个目标写了多少内存、映射了哪个模块。

对防守方，这意味着即使攻击者把 `ntdll` 的钩子摘了，内核仍然知道"某个进程往另一个进程里写了内存"。对攻击方，这意味着调用栈本身就是暴露点。

## 六、创建受保护的进程

PPL-AM 进程不是"调用某个 API 就能变成"的。保护级别由内核在创建时根据 PE 签名决定：

- 可执行文件必须由微软的反恶意软件证书签名。
- 由服务控制管理器启动，内核校验签名后按 `PsProtectedSignerAntimalware` 级别创建（也有 `-Light` 这个稍低的级别）。
- 进程一旦以 PPL-AM 运行，普通管理员无法 `OpenProcess` 拿到写权限，无法注入、无法读内存、无法结束。

这也解释了 EDR 为什么喜欢把核心服务做成 PPL-AM：它保护的不是检测能力，而是<mark>检测进程本身不被干掉</mark>。

## 七、规避 ETW-TI

从易到难：

1. **不打它关注的行为**。换注入方式，用间接的合法机制（DCOM、WMI、计划任务、服务）来执行，让事件看起来不像注入。
2. **调用栈伪造**。让事件里的 `CallStack` 指向合法模块里的 gadget，回溯出来的链是干净的。这是目前最有效的用户态手段——ETW-TI 报的是"谁调用了什么"，调用栈一假，归因就断了。
3. **减少跨进程写内存**。用 `NtMapViewOfSection` 共享节，复用目标进程已有的合法写入路径，或者干脆在同一进程内完成载荷执行（.NET 内存加载），从源头减少 `WriteVirtualMemory` 事件。
4. **内核层对抗**（需要驱动，还要对抗 PatchGuard）：
   - patch 内核里的 `EtwWrite` 相关路径。风险最高，PatchGuard 会检测内核代码段。
   - 找到 EDR 打开的 ETW 会话，关闭它或者覆盖它的会话句柄，让消费者收不到事件——也就是"追踪句柄覆盖"（Trace-Handle Overwriting）。内核里可以遍历 ETW 的内部会话结构，或者用未文档化的 `NtTraceControl` 操作。
   - 摘掉 EDR 在 ETW 上的注册（如果它用的是回调而非标准 consumer）。
5. **打 PPL-AM 进程本身**。保护它的是 Ob 回调（第 4 章），要动它得先摘回调（EDRSandBlast 这类路线），或者用 BYOVD。

现实约束：第 4、5 条需要内核执行权限，还要过 PatchGuard、HVCI、代码完整性几道关。在开了 HVCI 的机器上，内核代码 patch 基本不可行，剩下的空间主要是用户态的调用栈伪造和行为规避。

## 八、把这几章连起来

四层防护，覆盖四段时间和四种对象：

| 层 | 看什么 | 权限门槛 | 主要盲区 |
|---|---|---|---|
| 扫描器 | 磁盘上的文件 | 无 | 扫描间隙、纯内存载荷 |
| AMSI | 进入解释器的脚本 | 无（用户态） | 原生程序、已编译机器码 |
| ELAM | 启动阶段的 boot-start 驱动 | 微软 ELAM 签名 | 启动之后加载的驱动 |
| ETW-TI | 内核级运行时行为 | PPL-AM | 调用栈伪造、内核 patch |

防守方越往上走，可见度越高，实现成本也越高；攻击方越往下打，需要的权限越大，但一旦成功，覆盖也越彻底。

规避的本质不是"找漏洞"，而是<mark>找到对方看不见的那段时间和那一层</mark>。
